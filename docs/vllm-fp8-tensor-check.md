# vLLMのテンソル単位のFP8とエンジンの差の確認（計画）

[プリフィルのカーネルの確認](prefill-kernel-check.md)で、vLLMはブロック単位のFP8をL4でW8A16（Marlin）にし、プリフィルがbf16の1.30倍になること、読み込み時にテンソル単位にすればW8A8（CUTLASS）で0.68倍になることを確かめた。
1件ずつの時間なので、並行時に生成がどれだけ割り込まれるかと、精度は測っていない。ここでは、L4でvLLMを動かすときに設定で選べる手（FP8の形式）を、第2段階と同じ負荷で確かめ、同じインスタンスでTensorRT-LLM FP8と直接比べる。
第2段階では、TRT-LLM FP8（テンソル単位、W8A8）とvLLM FP8（ブロック単位、L4ではW8A16）の差が、エンジンの差かFP8の形式の差かを分けられなかった（[ADR-0009](adr/0009-batching-engines.md)の追記A5）。

| 問い | 手 | 変える記述 |
| --- | --- | --- |
| B：vLLMでFP8をテンソル単位で読み込むと、並行数4の割り込みはTRT-LLM FP8に並ぶか。精度は落ちないか | `--quantization fp8_per_tensor`（重みは`Qwen/Qwen3-8B`） | READMEの限界の表（「第2段階の選定は、エンジンの差とFP8の形式の差を分けられない」「並行時と精度は測っていない」）、原因の分析の「L4で確かめた」の「まだ言えないこと」 |
| C：TRT-LLMと同じModelOptのFP8をvLLMに読ませると、並行数4の割り込みはどれだけ違うか（エンジンの差） | vLLMに`Qwen3-8B-fp8-modelopt`（T1・T2と同じファイル）を渡す。`hf_quant_config.json`の`quant_algo`が`FP8`なので、vLLMはModelOptの形式として読む | 同上。Bで差が残ったときに、エンジンの差か量子化の作り方の差かを分ける |

第2段階の判定と選定は変えない。この構成は第2段階の候補ではない（同じ規則で選んだ構成ではない）ので、台数の判定はしない。
設計は、推論サービングと実験計画を専門とするサブエージェントの案を、設定で選べる手に絞って使った。

## 測らないもの

| 候補 | 測らない理由 |
| --- | --- |
| SGLangの食い違いが入力の書き換え（+100トークン）で起きたかの確認 | 書き換えは利用者が制御できない。確かめるには、組み立てたトークン列を`/v1/completions`へ送る新しい経路が要る。「エンジンごとに入力が変わるので`usage.prompt_tokens`を確かめる」という教訓は、確かめなくても使える |
| vLLMのチャンクの上限（`--max-num-batched-tokens`）の変更 | 約2,300トークンの入力では、上限2,048は「1回か2回に分けるか」の違いにしかならない。分けても生成が待つ計算の総量は同じで、増えるのは1ステップ分の固定費（TPOTで1ms前後の見込み）。選定も、READMEの「エンジンの既定値」の行（違いがあることだけを書いている）も変えない |
| vLLMのブロック単位のFP8（第2段階の構成）の測り直し | 問い（形式を選べばTRT-LLMに並ぶか）には要らない。第2段階の値（重なり1件あたり+19.3ms）は参考として並べる |
| 元の入力でのvLLM bf16の測り直し | 精度の基準は第2段階の記録を使う。vLLM bf16のインスタンスをまたいだ食い違いは3/1,000（第1段階⇔第2段階、`count_flips.py`） |

## 読み方

**指標**：①重なり1件あたりのTPOTの増え方（`scripts/tpot_prefill_overlap.py`。重なり0件と3件のTPOTの中央値の差÷3）、②TPOTの中央値、③TTFTの中央値。TTFT 2,000ms・TPOT 100msの超過の件数は報告するだけで、判定に使わない（TRT-LLM FP8の超過は第2段階で0件で、件数では差の大きさが分からない）。

**差がある**：B1（またはC）がT1・T2の両方と同じ側にあり、|B1 − T1とT2の平均| が「|T1 − T2|」と「大きい方の5%」の両方を超える。どちらかを満たさなければ「差は無い」。B1とCの間も、同じ2つの線（|T1 − T2|と5%）で比べる。
TRT-LLMは2回しか測らないので、|T1 − T2|はたまたま小さく出ることがあり、それだけでは差が無くても「差がある」になりやすい。誤りを止めているのは5%の線の方である。

**基準（T1・T2）**

| 結果 | 読み方 |
| --- | --- |
| ①か②で、\|T1 − T2\| が大きい方の15%を超える | 不確定。インスタンスの中のずれが大きく、B1・Cを読まない。そう書く |
| T1とT2の平均が第2段階（重なり1件あたり+8.5ms・TPOTの中央値64.3ms）から15%を超えて外れる | インスタンスの差として記録する（第1段階の2 → 59件と同じ扱い）。B1・CはT1・T2とだけ比べる |
| ModelOptのFP8のハッシュが第2段階と違う | チェックポイントが違うとして記録し、読み方は変えない（同じインスタンスの中の比較なので） |

**B1：vLLMのテンソル単位の速さ**（①で読む。②・③は並べて書き、①と向きが違えば、違ったことを書く）

| 結果 | 読み方 |
| --- | --- |
| 差は無い | vLLMでも、FP8をテンソル単位で読み込めば、並行数4の割り込みはTRT-LLM FP8に並ぶ。第2段階のvLLM FP8とTRT-LLM FP8の差は、主にFP8の形式（計算の形）による |
| B1が大きく、差がある | 形式をそろえても差が残る。計算側のスケール（TRT-LLMは事前に校正した静的な値、vLLMは実行時のトークンごとの値）、プリフィルと生成の組み方、エンジンの実装の違いを含み、分けない。第2段階のvLLM FP8（+19.3ms、別のインスタンス）と並べ、差のどれだけが縮んだかを参考として書く |
| B1が小さく、差がある | このワークロードでは、vLLMのテンソル単位のほうがTRT-LLM FP8より割り込みが小さい。そう書く |
| 起動のログのカーネルが`CutlassFP8ScaledMMLinearKernel`でない | 「別のカーネルで測った」として読み直す |

**C：同じModelOptのFP8でのエンジンの差**

| 結果 | 読み方 |
| --- | --- |
| 差は無い | 同じファイルを同じ方式（重みも入力も静的、テンソル全体で1つ）で読ませると、このワークロードの並行数4では、エンジンを替えても割り込みは変わらない |
| Cが大きく、差がある | エンジンの差がある。カーネル・プリフィルと生成の組み方・そのほかの実装の違いを含み、分けない |
| Cが小さく、差がある | 同じファイルなら、vLLMのほうがTRT-LLMより割り込みが小さい |
| 起動のログのカーネルが`CutlassFP8ScaledMMLinearKernel`でない | 「別のカーネルで測った」として読み直す |
| 起動のログに、まとめて計算する層（Q・K・Vなど）の入力のスケールが違うという警告が出る | vLLMは最大の値に合わせる。TRT-LLMの扱いは確かめていない。違いが残る点として書く |
| Cが起動しない | Cは読まない。B1の読み方はそのまま使う |

**B1とCを合わせた読み方**（B1とCの「差」は、上の定義でB1とCを比べる）

| C（TRT-LLMと比べて） | B1（Cと比べて） | 読み方 |
| --- | --- | --- |
| 差は無い | 差は無い | エンジンの差も量子化の作り方の差も見えない。第2段階の差は主にFP8の形式による |
| 差は無い | B1が大きい | エンジンの差は見えず、量子化の作り方（校正なしの重み＋動的なスケール 対 校正ありの重み＋静的なスケール）の差が効いた |
| Cが大きい | 差は無い | 量子化の作り方の差は見えず、エンジンの差が効いた |
| Cが大きい | B1が大きい | エンジンの差と量子化の作り方の差の両方がある |

上の表に無い組み合わせ（Cが小さいなど）は、そのまま数値を書く。台数の判定はしない。

**B2：テンソル単位の精度**

第2段階の足切りと同じ式で判定する（[ADR-0009](adr/0009-batching-engines.md)の5の段2：段1を通ったbf16＝vLLMとTRT-LLMの`ni`の、(ケース, 試行)ごとの平均を基準に、片側99.9%のt区間の下限が−2.6ptを超えるか）。基準のbf16は第2段階の記録で、インスタンスが違う。第2段階のFP8の下限はvLLM（ブロック単位）−2.08pt・TRT-LLM（テンソル単位）−1.43ptで、−2.6ptの線に近い。テンソル単位は重みのスケールがブロック単位より粗く、読み込み時の量子化は校正をしない。集計の前に、同じ基準で第2段階のvLLM FP8（−2.08pt）・TRT-LLM FP8（−1.43pt）が再現できることを確かめる。

| 結果 | 読み方 |
| --- | --- |
| 下限が−2.6ptを超える | このワークロードでは、テンソル単位で読み込んでも精度は落ちていない（落ちても2.6pt未満） |
| 下限が−2.6pt以下 | 精度が落ちていないとは示せなかった。速さだけでは勧めない。「差がある」とも書かない |
| B2が回らなかった（起動に失敗など） | 速さだけを書き、精度は測れなかったと書く |

参考として、vLLM bf16（第2段階）だけを基準にした下限と、食い違いの数（`count_flips.py`）も報告する。

**実務の結論（B1×B2）**：範囲はどの行も、L4・このワークロード・並行数4。台数の判定はしない。

| B1（TRT-LLM FP8と比べて） | B2 | 書く結論 |
| --- | --- | --- |
| 差は無い | 示せた | L4でvLLMのFP8を使うなら、テンソル単位で読み込めば、速さも精度もTRT-LLM FP8と同じ水準になる。第2段階の差は主にFP8の形式による |
| 差は無い | 示せなかった | 速さはTRT-LLMに並ぶが、精度が落ちていないとは示せなかった。テンソル単位を勧めない |
| B1が遅い | 示せた | 形式をそろえても速さの差が残る。原因はB1とCを合わせた読み方で書く。第2段階のvLLM FP8（ブロック単位）の値と並べ、どれだけ縮んだかを参考として書く |
| B1が遅い | 示せなかった | 勧めない |
| B1が速い | 示せた | このワークロードでは、vLLMのテンソル単位がTRT-LLM FP8より速く、精度も落ちていない |
| B1が速い | 示せなかった | 速いが、精度が落ちていないとは示せなかった。勧めない |
| どれでも | 回らなかった | 速さだけを書き、勧めるかは決めない |

**共通**：Bの重みは読み込み時にbf16から作ったもので、校正をしていない。計算側のスケールは実行時のトークンごとの値で（vLLM 0.31.0の`online/fp8.py`の`Fp8PerTensorOnlineLinearMethod`。CUTLASSのFP8が使えるGPUでは`kFp8DynamicTokenSym`）、TRT-LLMの静的な値とは違う。Cは、ModelOptのファイルの`input_scale`を静的なテンソル単位の値としてそのまま使う（`modelopt.py`の`quant_algo == "FP8"`、`KFp8StaticTensor`）。W8A8なので、重みに加えて各層への入力も8bitに丸められる（第2段階のvLLM FP8は16bitのまま計算した）。B2の精度が第2段階のvLLM FP8と違っても、重みのスケールの粗さと入力の丸めのどちらが効いたかは分けない。そう明記する。

## 手順

[GPUでの実行の手順](gpu-runbook.md)のapply・destroyはそのまま使い、`local.sh`の準備とセルで回す。自動シャットダウンは300分（`auto_shutdown_minutes=300`）。
