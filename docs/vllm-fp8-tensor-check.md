# vLLMのテンソル単位のFP8の確認（計画）

[プリフィルのカーネルの確認](prefill-kernel-check.md)で、vLLMはブロック単位のFP8をL4でW8A16（Marlin）にし、プリフィルがbf16の1.30倍になること、読み込み時にテンソル単位にすればW8A8（CUTLASS）で0.68倍になることを確かめた。
1件ずつの時間なので、並行時に生成がどれだけ割り込まれるかと、精度は測っていない。ここでは、L4でvLLMを動かすときに設定で選べる手（FP8の形式）を、第2段階と同じ負荷で確かめる。

| 問い | 手 | 変える記述 |
| --- | --- | --- |
| FP8をテンソル単位で読み込むと、並行数4の割り込みはW8A8の帯に入るか。精度は落ちないか | `--quantization fp8_per_tensor`（重みは`Qwen/Qwen3-8B`） | 原因の分析の「L4で確かめた」の「まだ言えないこと」、READMEの限界の表（並行時と精度は測っていない） |

第2段階の判定と選定は変えない。この構成は第2段階の候補ではない（同じ規則で選んだ構成ではない）ので、台数の判定はしない。
この文書の「予想」と「読み方」は測る前に書いた（2026-11-19。2026-11-21にチャンクの上限の問いを外した）。設計は、推論サービングと実験計画を専門とするサブエージェントの案を、設定で選べる手に絞って使った。

## 測らないもの

| 候補 | 測らない理由 |
| --- | --- |
| SGLangの食い違いが入力の書き換え（+100トークン）で起きたかの確認 | 書き換えは利用者が制御できない。確かめるには、組み立てたトークン列を`/v1/completions`へ送る新しい経路が要る。「エンジンごとに入力が変わるので`usage.prompt_tokens`を確かめる」という教訓は、確かめなくても使える |
| vLLMのチャンクの上限（`--max-num-batched-tokens`）の変更 | 約2,300トークンの入力では、上限2,048は「1回か2回に分けるか」の違いにしかならない。分けても生成が待つ計算の総量は同じで、増えるのは1ステップ分の固定費（TPOTで1ms前後の見込み）。選定も、READMEの「エンジンの既定値」の行（違いがあることだけを書いている）も変えない |
| 元の入力でのvLLM bf16の測り直し | 精度の基準は第2段階の記録を使う。vLLM bf16のインスタンスをまたいだ食い違いは3/1,000（第1段階⇔第2段階、`count_flips.py`） |

## 予想（測る前）

| 項目 | 予想 | 根拠 |
| --- | --- | --- |
| R1・R2 | 第2段階のvLLM FP8に近い（重なり1件あたり+19.3ms、TPOTの中央値94ms、超過328件） | 同じ構成・同じ測り方。インスタンスが違うので、超過の件数は大きく動き得る |
| B1の重なり1件あたりの増え方 | 約10〜11ms（±約3） | 第2段階の9構成の直線（増え方＝0.142＋0.0209×並行数1のTTFT、残差のSD 1.34ms）に、B1の並行数1のTTFTの推定490〜530ms（プリフィルの確認の比0.68×第2段階のvLLM bf16 776ms、0.53×vLLM FP8 931ms）を入れた |

| B2の精度 | 不明（境目に近い） | 第2段階のFP8の下限はvLLM（ブロック単位）−2.08pt・TRT-LLM（テンソル単位）−1.43ptで通り、SGLang（ブロック単位）は示せなかった（[ADR-0009](adr/0009-batching-engines.md)の追記A2）。テンソル単位は重みのスケールがブロック単位より粗い。読み込み時の量子化は校正をしない |

## 読み方（測る前に決めた）

**指標**：①重なり1件あたりのTPOTの増え方（`scripts/tpot_prefill_overlap.py`。重なり0件と3件のTPOTの中央値の差÷3）、②TPOTの中央値、③TTFTの中央値。TTFT 2,000ms・TPOT 100msの超過の件数は報告するだけで、判定に使わない（fp8-blockのTPOTの中央値94msは100msの線のすぐ下にあり、件数は小さなずれを大きく見せる）。

**基準（R1・R2）**

| 結果 | 読み方 |
| --- | --- |
| ①か②で、\|R1 − R2\| が大きい方の15%を超える | 不確定。インスタンスの中のずれが大きく、B1を読まない。そう書く |
| R1とR2の平均が第2段階（TPOTの中央値94ms・超過328件）から大きく外れる（超過が100未満か600を超える） | インスタンスの差として記録する（第1段階の2 → 59件と同じ扱い）。B1はR1・R2とだけ比べる |

**B1：テンソル単位の速さ**（比べる相手はR1とR2。第2段階の他エンジンの値とは、インスタンスが違うので参考として並べるだけ）

| ①の値 | 読み方 |
| --- | --- |
| 12.7ms以下（第2段階のW8A8の帯の上端＝SGLang FP8） | 同じvLLMでも、W8A8にすると割り込みはW8A8の帯に入った。原因の分析の「律速」を、記録の上の関連（r = 0.92）から、同じエンジンで条件を変えた確認に上げる |
| 15.3ms以上（W4A16とbf16の帯の下端） | 計算の形だけでは並行時の差を説明できない。そう書く |
| その間 | 不確定 |
| 起動のログのカーネルが`CutlassFP8ScaledMMLinearKernel`でない | 「別のカーネルで測った」として読み直す |

**B2：テンソル単位の精度**

第2段階の足切りと同じ式で判定する（[ADR-0009](adr/0009-batching-engines.md)の5：第2段階の3つのbf16の`ni`の平均を基準に、片側99.9%のt区間の下限が−2.6ptを超えるか）。基準のbf16は第2段階の記録で、インスタンスが違う。

| 結果 | 読み方 |
| --- | --- |
| 下限が−2.6ptを超える | このワークロードでは、テンソル単位で読み込んでも精度は落ちていない（落ちても2.6pt未満）。B1と合わせて、L4でvLLMのFP8を使うなら、テンソル単位で読み込むほうがよいと書く。ただし台数は判定しない |
| 下限が−2.6pt以下 | 精度が落ちていないとは示せなかった。速さだけでは勧めない。「差がある」とも書かない |
| B2が回らなかった（起動に失敗など） | 速さだけを書き、精度は測れなかったと書く |

参考として、vLLM bf16（第2段階）だけを基準にした下限と、食い違いの数（`count_flips.py`）も報告する。

**共通**：Bの重みは読み込み時にbf16から作ったもので、ModelOptのテンソル単位のチェックポイントではない。計算側のスケールは実行時のトークンごとの値で、TRT-LLMの静的な値とは違う。そう明記する。
