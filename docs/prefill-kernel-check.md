# プリフィルのカーネルの確認（計画と実施の記録）

[原因の分析](analysis-batching.md)で推定にとどめた2点を、L4の上でvLLMのプリフィルの時間を測って確かめる。

1. vLLMがブロック単位のFP8をL4でW8A16（Marlin）にすると、プリフィルはbf16より遅いが、生成（1トークンずつ）は速い
2. 計算もFP8で行う形（W8A8）なら、同じvLLMでもプリフィルがbf16より軽くなる

第2段階の判定や選定は変えない。これは原因の確認で、結果は[原因の分析](analysis-batching.md)に追記する。
この文書の「予想」と「読み方」は測る前に書いた（2026-11-18。同じ日に、測る前のレビューを受けて読み方の定義・反証の行・プロファイラを足した）。

## 測り方

| 条件 | 値 |
| --- | --- |
| インスタンス | `g6.xlarge`（L4 1台）。第2段階と同じTerraform |
| エンジン | vLLM 0.31.0（`scripts/gpu/pins.sh`）。ほかのエンジンは入れない |
| 送り方 | 1件ずつ（並行数1）。プロンプトはランダムなトークン列で、プレフィックスキャッシュは切る。チャンクの上限は第2段階と同じ2,048 |
| 長さ | 16・64・128・256・512・1,024・2,048・2,304トークン（2,304は評価セットの中央値に近く、2,048＋256の2つのチャンクに分かれる） |
| 測るもの | `max_tokens=1`の`llm.generate()`の時間＝プリフィル（＋1回のサンプリング）。2,048トークンで65トークン生成した時間との差を64で割って、生成1トークンの時間 |
| 回数 | 長さごとにウォームアップ3回＋10回の中央値。5構成を順に回し、逆の順でもう1周する（時間による変化を構成の差と分けるため） |
| カーネルごとの時間 | 時間を測った後、同じプロセスで2,048トークンのプリフィルを1回、torchのプロファイラを付けて流す（線形層と注意機構の時間を分ける） |
| 選ばれたカーネル | vLLMの起動のログの`Selected ... for ...`・`Using ... for ...`の行で確かめる。TritonのW8A8で、L4向けの調整済みの設定が無いときの警告も拾う |
| GPUの状態 | 0.5秒ごとのクロック・温度・電力・電力上限・クロックが下がった理由（`gpu.csv`）。各回の開始時刻を記録し、突き合わせられるようにする |

プリフィルでは、一度に処理するトークンの数（行列計算のM）がプロンプトの長さ（最大2,048）になる。生成ではMが1になる。
CUDA Graphで動くのは短い長さだけなので、構成どうしは同じ長さの中だけで比べる。

vLLMは、チェックポイントの`config.json`にある量子化の設定（形式）とGPUを見て、線形層のカーネルを優先順の一覧から自動で選ぶ。
`--linear-backend`を指定すると、その系統のカーネルに絞れる。

| 構成 | モデル | 引数 | L4で選ばれる見込みのカーネル | 計算の形 | 位置づけ |
| --- | --- | --- | --- | --- | --- |
| bf16 | `Qwen/Qwen3-8B` | なし | （量子化なし） | bf16 | 基準 |
| fp8-block | `Qwen/Qwen3-8B-FP8` | なし（第2段階と同じ） | `MarlinFP8ScaledMMLinearKernel` | W8A16 | 第2段階の再現 |
| fp8-tensor | `Qwen/Qwen3-8B` | `quantization="fp8_per_tensor"`（読み込み時に重みをテンソル単位のFP8へ） | `CutlassFP8ScaledMMLinearKernel` | W8A8（重みはテンソル単位、計算側はトークン単位の動的なスケール） | **形式を選ぶ手**（カーネルは自動） |
| fp8-block-triton | `Qwen/Qwen3-8B-FP8` | `linear_backend="triton"` | `TritonFp8BlockScaledMMKernel` | W8A8（ブロック単位） | カーネルを指定する手（ふつうは使わない。参考） |
| awq | `Qwen/Qwen3-8B-AWQ` | なし | `MarlinLinearKernel` | W4A16 | 重みだけ小さくする形の比較 |

fp8-tensorは、TensorRT-LLMのFP8と2点で違う。TensorRT-LLMは計算側のスケールを事前に校正した静的な値で、行列全体に1つ持つ。fp8-tensorは実行時にトークンごとに求める。
fp8-block-tritonは、L4向けに調整された設定が無く、既定の設定で動く。

## 予想（測る前）

| 構成 | 短いプロンプト（16〜64） | 長いプロンプト（2,048と2,304） | 生成1トークン |
| --- | --- | --- | --- |
| fp8-block（W8A16） | bf16より速いか同じ | **bf16より遅い**（第2段階の並行数1のTTFTの中央値は931 対 776ms、比1.20） | **bf16より速い**（第2段階のTPOTの中央値は35 対 62ms） |
| fp8-tensor（W8A8） | 不明 | **bf16より速い**（TensorRT-LLMのFP8は434 対 746ms、比0.58） | bf16より速い |
| fp8-block-triton（W8A8） | 不明 | fp8-blockより速い | 不明 |
| awq（W4A16） | bf16より速い | bf16と同じか遅い | 最も速い |

## 読み方（測る前に決めた）

**用語の定義**

| 用語 | 定義 |
| --- | --- |
| 周のずれ | 同じ構成・同じ長さでの、1周目と2周目の中央値の差の絶対値 |
| 差がある | 2つの周の両方で同じ向きで、差が「2つの構成の周のずれの大きい方」と「遅い方の5%」の両方を超える。どちらかを満たさなければ「差は無い」 |
| 長いプロンプトで速い・遅い | 2,048と2,304の両方で差がある。片方だけなら「不明」 |
| 比 | 2,304トークンでの、ある構成の時間 ÷ bf16の時間（2つの周の平均） |

**まず、この測り方で第2段階を再現できたか**

| 結果 | 読み方 |
| --- | --- |
| fp8-blockが長いプロンプトでbf16より遅い | 再現できた。下の表に進む。比を第2段階の1.20と並べる |
| fp8-blockが長いプロンプトでbf16より遅くない | 再現できなかった。1件ずつの時間では第2段階の差を捉えられていない（第2段階の時間はサーバーとクライアントの間の時間も含む）。推定1・2はこの測定からは読まない。そう書く |

**推定1・2**

| 結果 | 読み方 |
| --- | --- |
| fp8-blockが長いプロンプトで遅く、生成1トークンでは速い | 推定1を確かめた（Mが大きいときだけ遅い）。どの長さで逆転するかを書く |
| fp8-blockが生成1トークンでもbf16より速くない | 推定1の「生成は速い」は確かめられなかった。分析の文書を直す |
| fp8-blockが短いプロンプトでも遅い | Mの大きさに依らずW8A16が不利。分析の文書の「Mが大きい形に向かない」を直す |
| fp8-tensorが長いプロンプトでbf16より速い | 推定2を確かめた。比が0.79以下（TensorRT-LLMの0.58と1.0の中点より0.58に近い）なら「第2段階のFP8の差の大部分は計算の形で説明できる」、0.79を超えるなら「一部だけ説明できる」と書く |
| fp8-tensorが長いプロンプトでbf16より速くない | 推定2は確かめられなかった。TensorRT-LLMのFP8が速かったのは、静的なスケールやエンジンの実装など別の理由の可能性がある。そう書く |
| fp8-block-tritonが長いプロンプトでfp8-blockより速い | L4では、vLLMの既定の優先順（MarlinがTritonのW8A8より先）がこのワークロードに合っていない可能性がある。手の候補は「形式を選ぶ（fp8-tensor）」と「カーネルを指定する（fp8-block-triton）」の2つ。並行時の速さと精度は測っていないので、どちらを選ぶかの結論にはしない |
| fp8-block-tritonが長いプロンプトでfp8-blockより速くない | 何も言わない。調整していない設定で動いたので、AdaでのブロックのW8A8の向き不向きは分からない |
| fp8-block-tritonとfp8-tensorの、長いプロンプトでの速さ | 2つの手のどちらがプリフィルを軽くするかとして並べる。主に見るのはfp8-tensor（ふつうの手） |
| 起動のログのカーネルが上の表と違う | 見込みのカーネルの列を直し、その構成は「別のカーネルで測った」として読む |

**カーネルごとの時間（プロファイラ）**

2,048トークンのプリフィル1回のGPUの時間を、線形層の行列計算（bf16はcuBLAS、ほかはMarlin・CUTLASS・Tritonのカーネル）・注意機構・それ以外に分けて表にする。
fp8-blockとbf16の時間の差の大部分が線形層の差なら、「遅いのは線形層のカーネル（Marlin）」と書く。Marlinは重みを16bitに戻す処理を同じカーネルの中で行うので、「戻す手間」と「カーネルの作り」のどちらが効いたかは分けられない。そう書く。

並行数4での超過（台数の判定）と精度は測らない。1件ずつの時間から台数は出せない。

## 時間と費用（推定）

| 内容 | 時間 |
| --- | --- |
| vLLMの環境（`uv pip install`） | 約5〜10分 |
| モデル3つ（約30GB）のダウンロード | 約5〜10分 |
| 5構成×2周（起動とCUDA Graphの取り込み 約2〜3分＋測定 約3分＋プロファイラ 約1分） | 約60〜70分 |
| 合計 | **約1.2〜1.5時間、約$1.4〜1.8**（$1.167/時間） |

自動シャットダウンは2時間（`auto_shutdown_minutes=120`）にする。1つの構成が失敗しても、残りの構成は回し、`DONE`に失敗した構成を書く。準備で失敗したときは`FAILED`を書いて止まる（どちらの場合も`RUNNING`は消えるので、`collect`が止まる）。

## 手順

[GPUでの実行の手順](gpu-runbook.md)のapply・destroyはそのまま使い、準備とセルの代わりに次を回す。

```bash
scripts/gpu/local.sh push    <ip>
scripts/gpu/local.sh prefill <ip>
scripts/gpu/local.sh collect <ip> runs/prefill-<date>
```

結果は`<dest>/prefill/<構成>-r<周>.json`（各回の時間と開始時刻、中央値）、選ばれたカーネルは`<構成>-r<周>.kernels.txt`、プロファイラは`<dest>/prefill/profile/<構成>-r<周>/`、失敗した構成は`<dest>/prefill/failed.txt`。
