# プリフィルのカーネルの確認（計画）

[原因の分析](analysis-batching.md)で推定にとどめた2点を、L4の上でvLLMのプリフィルの時間を測って確かめる。

1. vLLMがブロック単位のFP8をL4でW8A16（Marlin）にすると、プリフィルはbf16より遅いが、生成（1トークンずつ）は速い
2. 計算もFP8で行う形（W8A8）なら、同じvLLMでもプリフィルがbf16より軽くなる

第2段階の判定や選定は変えない。これは原因の確認で、結果は[原因の分析](analysis-batching.md)に追記する。
この文書の「予想」と「読み方」は測る前に書いた（2026-11-18）。

## 測り方

| 条件 | 値 |
| --- | --- |
| インスタンス | `g6.xlarge`（L4 1台）。第2段階と同じTerraform |
| エンジン | vLLM 0.31.0（`scripts/gpu/pins.sh`）。ほかのエンジンは入れない |
| 送り方 | 1件ずつ（並行数1）。プロンプトはランダムなトークン列で、プレフィックスキャッシュは切る。チャンクの上限は第2段階と同じ2,048 |
| 長さ | 16・64・256・1,024・2,048・2,304トークン（2,304は評価セットの中央値に近く、2つのチャンクに分かれる） |
| 測るもの | `max_tokens=1`の`llm.generate()`の時間＝プリフィル（＋1回のサンプリング）。2,048トークンで65トークン生成した時間との差を64で割って、生成1トークンの時間 |
| 回数 | 長さごとにウォームアップ3回＋10回の中央値。5構成を順に回し、逆の順でもう1周する（時間による変化を構成の差と分けるため） |
| 選ばれたカーネル | vLLMの起動のログの`Selected ... for ...`の行で確かめる |

プリフィルでは、一度に処理するトークンの数（行列計算のM）がプロンプトの長さ（最大2,048）になる。生成ではMが1になる。

vLLMは、チェックポイントの`config.json`にある量子化の設定（形式）とGPUを見て、線形層のカーネルを優先順の一覧から自動で選ぶ。
`--linear-backend`を指定すると、その系統のカーネルに絞れる。

| 構成 | モデル | 引数 | L4で選ばれる見込みのカーネル | 計算の形 | 位置づけ |
| --- | --- | --- | --- | --- | --- |
| bf16 | `Qwen/Qwen3-8B` | なし | （量子化なし） | bf16 | 基準 |
| fp8-block | `Qwen/Qwen3-8B-FP8` | なし（第2段階と同じ） | `MarlinFP8ScaledMMLinearKernel` | W8A16 | 第2段階の再現 |
| fp8-tensor | `Qwen/Qwen3-8B` | `quantization="fp8"`（読み込み時にテンソル単位へ量子化） | `CutlassFP8ScaledMMLinearKernel` | W8A8（テンソル単位、計算側のスケールは動的） | **形式を選ぶ手**（カーネルは自動） |
| fp8-block-triton | `Qwen/Qwen3-8B-FP8` | `linear_backend="triton"` | `TritonFp8BlockScaledMMKernel` | W8A8（ブロック単位） | カーネルを指定する手（ふつうは使わない。参考） |
| awq | `Qwen/Qwen3-8B-AWQ` | なし | Marlin（W4A16） | W4A16 | 重みだけ小さくする形の比較 |

fp8-tensorは、TensorRT-LLMのFP8（ModelOptで校正した静的なスケール）と同じではない。計算側のスケールを実行時に求めるので、その分だけ重い。

## 予想（測る前）

| 構成 | 短いプロンプト（16〜64） | 長いプロンプト（2,048〜2,304） | 生成1トークン |
| --- | --- | --- | --- |
| fp8-block（W8A16） | bf16より速いか同じ | **bf16より遅い**（第2段階の並行数1のTTFTは931 対 776ms） | bf16より速い（第2段階のTPOTは35 対 62ms） |
| fp8-block-triton（W8A8） | 不明 | fp8-blockより速い | 不明 |
| fp8-tensor（W8A8） | 不明 | **bf16より速い**（TensorRT-LLMのFP8は434 対 746ms） | bf16より速い |
| awq（W4A16） | bf16より速い | bf16と同じか遅い | 最も速い |

## 読み方（測る前に決めた）

比べるのは同じ周の中の中央値と、2周の両方で同じ向きになるか。差が2周の間のずれより小さければ「差は無い」と読む。

| 結果 | 読み方 |
| --- | --- |
| fp8-blockが長いプロンプトでbf16より遅く、短いプロンプトでは遅くない | 推定1を確かめた（Mが大きいときだけ遅い） |
| fp8-blockが短いプロンプトでも遅い | 「Mが大きい形に向かない」ではなく、W8A16のどの形でも戻す手間が勝っている。分析の文書の理由を直す |
| fp8-tensorが長いプロンプトでbf16より速い | 推定2を確かめた。第2段階のFP8の差は、エンジンの差より計算の形の差という読みを支える |
| fp8-tensorが長いプロンプトでbf16より速くない | 推定2は確かめられなかった。TensorRT-LLMのFP8が速かったのは、静的なスケールやエンジンの実装など別の理由の可能性がある。そう書く |
| fp8-block-tritonが長いプロンプトでfp8-blockより速い | L4では、vLLMの既定の優先順（MarlinがTritonのW8A8より先）がこのワークロードに合っていない可能性がある。手の候補は「形式を選ぶ（fp8-tensor）」と「カーネルを指定する（fp8-block-triton）」の2つ。並行時の速さと精度は測っていないので、どちらを選ぶかの結論にはしない |
| fp8-block-tritonとfp8-tensorの、長いプロンプトでの速さ | 2つの手のどちらがプリフィルを軽くするかとして並べる。主に見るのはfp8-tensor（ふつうの手） |
| 起動のログのカーネルが上の表と違う | 見込みのカーネルの列を直し、その構成は「別のカーネルで測った」として読む |

並行数4での超過（台数の判定）までは測らない。1件ずつの時間から台数は出せない。

## 時間と費用（推定）

| 内容 | 時間 |
| --- | --- |
| vLLMの環境（`uv pip install`） | 約5〜10分 |
| モデル3つ（約30GB）のダウンロード | 約5〜10分 |
| 5構成×2周（起動とCUDA Graphの取り込み 約2〜3分＋測定 約2分） | 約45〜50分 |
| 合計 | **約1〜1.2時間、約$1.2〜1.4**（$1.167/時間） |

自動シャットダウンは2時間（`auto_shutdown_minutes=120`）にする。

## 手順

[GPUでの実行の手順](gpu-runbook.md)のapply・destroyはそのまま使い、準備とセルの代わりに次を回す。

```bash
scripts/gpu/local.sh push    <ip>
scripts/gpu/local.sh prefill <ip>
scripts/gpu/local.sh collect <ip> runs/prefill-<date>
```

結果は`<dest>/prefill/<構成>-r<周>.json`（各回の時間と中央値）、選ばれたカーネルは`<構成>-r<周>.kernels.txt`。
