# ADR-0008: 量子化の非劣化を確かめ、llama.cppの4bitも測ってから構成を選ぶ

- Status: Accepted
- Date: 2026-10-26

## 結論

- 各エンジンの中で、4bitが自分のbf16より2.6pt以上悪くないか（非劣化）を確かめる。greedy・200件×5試行で、片側99.5%のt区間の下限で判定する。
- llama.cpp Q4_K_Mも自前で作って測る。
- 選び方は、精度の足切り → 会話用の基準を満たす最大の並行数 → 目標の並行数ごとに台数が最も少ない構成。同じ台数なら並べて決めない。判定不能は数えない（追記2026-10-26）。
- 結果（追記2026-10-26）：vLLM AWQは非劣化を示せた（下限 −2.48pt）、llama.cpp Q4_K_Mは示せなかった（−4.05pt）。目標の並行数が4以上ならvLLM AWQが最も少ない台数。

## Context

本番2回（速さの測定・普通の精度の測定と第3パス）で、決めてあった測定は終わった。構成を1つ選ぶ段階で、2つの穴が見つかった。
（決定日 2026-10-26）<!-- gbrain: [Source: User, 本番の結果のまとめ方の相談, 2026-10-26] -->

1. **量子化の精度を確かめていない。** 会話用の基準（ADR-0003）を守れる最大の並行数は、vLLM AWQが4、vLLM bf16が2で、AWQなら台数が半分で済む。
   選定はAWQに傾くが、AWQが精度を失っていないかは確かめていない。普通の精度の測定は判定しない設計で（README）、temperature 0.7なので量子化の差を切り出せない。
2. **4bitを測ったのがvLLMだけ。** llama.cppはbf16しか測っていない。このままAWQを選ぶと、量子化したvLLMと量子化していないllama.cppを比べたことになり、
   どの構成を測るかをエンジン名で決めた形になる。

| | bf16 | 4bit |
| --- | --- | --- |
| vLLM | 測った（最大並行数2） | 測った（最大並行数4） |
| llama.cpp | 測った（最大並行数1） | **測っていない** |

2026-08-30・2026-10-19に、llama.cppの4bit（GGUF Q4_K_M）を外した理由は「4bit同士をエンジンの間で比べると、差がエンジンか量子化方式か区別できない」だった
（計画書のレイヤー構成、ADR-0002の追記2026-10-19）。今回は、エンジンの優劣を言うためではなく、**実務で選べる構成の比較**として測るので、この理由とは矛盾しない。
各エンジンの中のbf16と4bitの比較は、エンジンを跨がない。

**前提となる見方と、その強さ**：「並行稼働ではvLLMが強い」という見方は、仕組み（PagedAttention、Kwon et al. SOSP 2023）とベンダー・個人のベンチマーク
（Red Hat 2025・2026、Docker 2025 ほか）がそろって示している。ただし、同じGPUで両者の設定をそろえた査読付きの比較は見当たらない。Red HatはvLLMの製品を扱う側で、
llama.cppの並行スロットの設定を書いていない。llama.cppのサーバーも並行スロットと連続バッチングを持つ（既定で有効）。この見方は自分のデータで確かめる対象であり、
bf16の比較（ADR-0003のI節）では見方どおりだった（並行数2から差が出た）。

## 検討した案

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 今の結果のままクローズし、量子化の精度とllama.cppの4bitは限界として書く | 却下 | 選定の結論（AWQ）が、確かめていない前提に乗る。llama.cppの4bitを測らないのは、構成をエンジン名で選んだ形になる |
| 普通の精度の測定（temperature 0.7）の結果で、量子化の差を判定する | 却下 | 結果を見た後に判定の方法を決めることになる。サンプリングの揺れも混ざる |
| vLLM AWQ・llama.cpp bf16のgreedyは本番2回目の結果を流用し、bf16（vLLM）と4bit（llama.cpp）だけ回す | 却下 | 別のインスタンス・別の日の値になり、流用する側の値はもう見ている。測り直しの追加は約1.8時間 |
| Qwen公式の`Qwen/Qwen3-8B-GGUF`のQ4_K_Mを使う | 却下 | 埋め込まれたチャットテンプレートが自前のbf16 GGUFと違うと、ツール呼び出しのプロンプトが変わり、重み以外の差が混ざる |
| 非劣化の区間を、普通の片側97.5%にする | 却下 | 下のシミュレーションで、誤りの率が2.5〜7.6%に膨らむ |
| 片側99%にする（ρ ≤ 0.1の範囲で誤りの率を守る） | 却下 | ρの推定（0.13〜0.16）が、すでに範囲の外 |
| 片側99.9%にする（どの条件でも誤りの率を守る） | 却下 | 示せる確率が約4割まで下がる |
| 「劣化が示された」も判定に加える | 却下 | 非劣化の試験の判定は「示せた／示せなかった」の2つが普通で、劣化の判定には別の基準が要る |

## Decision

### 1. 回すセル（1回のapply）

| 目的 | セル | パス |
| --- | --- | --- |
| 量子化の非劣化 | vLLM bf16・vLLM AWQ・llama.cpp bf16・llama.cpp Q4_K_M の並行数1 | `accuracy_under_load`、greedy、200件×5試行、seed_base 0（第3パスと同じツールの並び順） |
| llama.cpp Q4_K_Mの容量 | 並行数 1・2・4・8・16・32 | `latency`、1,000件（ADR-0003。llama.cpp bf16と同じ水準） |
| インスタンスの個体差 | vLLM AWQ の並行数4 | `latency`、本番1回目と同じセル |

- 並び順は、本番の一覧と同じく、固定のseedでランダムにする（ADR-0007）。一覧は`make_main_cells.py`の出力にし、手で書き換えない。
- **Q4_K_Mは自前で作る**：本番のbf16 GGUFから、`pins.sh`で固定したllama.cppの`llama-quantize`で作る（imatrixは使わない）。ハッシュを記録する。
- 個体差のセルは1つにする。本番1回目で判定の境目に近かったのは、vLLM AWQの並行数4（超過2/1,000、上限0.63%）とvLLM bf16の並行数2（3/1,000、0.77%）で、
  llama.cppのbf16（並行数1は0件、2は18.7%）は遠い。llama.cpp Q4_K_Mが並ぶとしたら相手はvLLM AWQの「4」なので、このセルで、インスタンスの速さの差
  （本番1回目と同じセルのp50・p99と、`gpu.csv`のクロック）と、選定に効く判定が保たれるかの両方を見る。
  vLLM AWQの並行数4の判定が本番1回目と変わったら報告し、llama.cpp Q4_K_Mとの比較には同じapplyの値を使う。測り直しはしない。

### 2. 量子化の非劣化の規則

| 項目 | 決定 |
| --- | --- |
| 問い | 各エンジンで、4bitはbf16より2.6pt以上悪くないか（片側） |
| マージン | −2.6pt（ADR-0002と同じ。量子化の損がモデル1段階分を超えるなら、bf16の4Bを使うほうがよい） |
| 指標 | selection（呼ぶべきでない場面で呼ばないことを含む）。arg_exactは推定値とCIを報告するだけで、判定に使わない |
| 方法 | ケースごとの差（5試行の平均、4bit − bf16）の平均に、**片側99.5%のt区間**の下限を付ける |
| 判定 | 下限 > −2.6pt なら「非劣化を示せた」、それ以外は「示せなかった」 |
| 方法の前提の確かめ | 回した後、入れ替わった組の割合 p_d ≥ 4.5%、ケース内相関 ρ ≤ 0.3（分散分析型の推定）を確かめる。外れたら「示せなかった」として扱う |
| 件数 | 200件×5試行で固定。結果を見て足さない |

**99.5%にした理由**：守りたい誤りの率は2.5%（片側）のままである。今回の条件では、入れ替わりが少なく片方向に偏るので、ケースごとの差の平均が正規分布に近づかず、
97.5%の区間では実際の誤りの率が2.5%を超える。区間を広げて、実際の誤りの率を2.5%以下に戻した（ADR-0002の追記2026-10-15の案B）。

**シミュレーション**（`scripts/power_simulation.py`の`simulate_case_diffs`。200件×5試行、各8,000回。誤りの率は本当の差が−2.6ptのときに「示せた」とする割合）：

| p_d | ρ | 誤りの率：97.5% / 99% / 99.5% / 99.9% | 示せる確率（本当の差 −0.7pt）：同じ順 |
| --- | --- | --- | --- |
| 3% | 0〜0.5 | 4.1〜7.6% / 2.2〜5.2% / 1.3〜4.1% / 0.4〜2.3% | 0.85〜0.92 / 0.77〜0.86 / 0.71〜0.80 / 0.59〜0.64 |
| 4.5% | 0〜0.3 | 3.1〜5.4% / 1.5〜3.3% / 0.8〜2.3% / 0.3〜1.0% | 0.77〜0.80 / 0.67〜0.69 / 0.59〜0.60 / 0.39〜0.42 |
| 6% | 0〜0.3 | 2.5〜4.5% / 1.1〜2.6% / 0.5〜1.7% / 0.2〜0.5% | 0.68〜0.69 / 0.54〜0.56 / 0.45〜0.46 / 0.28〜0.30 |
| 8% | 0〜0.3 | 2.6〜3.9% / 1.1〜1.8% / 0.6〜1.2% / 0.1〜0.3% | 0.57 / 0.42〜0.44 / 0.33〜0.34 / 0.17〜0.19 |

McNemar型のクラスター補正（Obuchowski 1998・Yang ほか 2010。上記スクリプトの`shifted`・`yang`）も、200件ではt区間とほぼ同じ誤りの率になり、補正は要る。

**p_dとρの見積もり**（本番2回目と予備の実行から。greedyでbf16とAWQを比べた組は無いので、近い組で代用した。計画にだけ使い、判定には使わない）：

| 組 | 入れ替わった組 | 入れ替わりのあるケース | 差 | ρ（95%の幅、ケースの引き直し） |
| --- | --- | --- | --- | --- |
| greedy：vLLM AWQ vs llama.cpp bf16（量子化＋エンジン） | 45/1,000（4.5%） | 31/200 | −0.7pt | 0.16（0.06〜0.24） |
| temperature 0.7：vLLM bf16 vs vLLM AWQ（量子化＋サンプリング） | 45/1,000（4.5%） | 33/200 | −0.7pt | 0.13（0.04〜0.21） |
| greedy A/A：vLLM AWQ 並行数1（pilot-1 vs 本番2回目） | 2/1,000 | 2/200 | −0.2pt | — |
| greedy A/A：llama.cpp bf16 並行数1（pilot-2 vs 本番2回目） | 0/1,000 | 0/200 | 0 | — |

本当の差が−0.7pt前後なら、示せる確率は約6割である。

### 3. 構成の選び方（結果を見る前に決める）

1. **精度の足切り**：bf16の構成は基準なので通る。4bitの構成は、2の判定で「非劣化を示せた」ときだけ通る。
2. **容量**：会話用の基準を守れる最大の並行数（ADR-0003）から、目標の同時リクエスト数ごとに必要な台数を出す。
   目標の並行数は決めていなかったので、1・2・4・8・16の表で示す。
3. **選ぶ**：足切りを通った構成のうち、必要な台数が最も少ないもの。同じ台数なら、並べて示し、どちらとも決めない。
4. 足切りを通らなかった4bitの構成は、容量と「精度は示せなかった」を並べて、引き換えとして報告する。

## 検討した懸念

| 懸念 | 対処 |
| --- | --- |
| 結果を見てから追加の測定を決めている | 追加するのは、選定が乗っている未確認の前提（量子化の精度）と、測っていなかった構成（llama.cppの4bit）だけ。規則は回す前にこのADRで固定する |
| 勝った構成だけを追加で確かめることになりうる | 量子化の非劣化は両エンジンで行う。llama.cppの4bitも測る |
| 99.5%は自分で決めた補正である | 守る誤りの率（2.5%）は変えていない。補正の量と、それを決めたシミュレーションの条件を上に書き、回した後に条件の範囲に入っているかを確かめる |
| ±2.6ptは業界の量子化の基準（元の精度の99%以上の回復など）より緩い | そのとおりで、限界として書く。200件では99%の回復は示せない（ADR-0002で却下した経緯） |
| 別のインスタンスで測った速さを比べている | 選定に効く境目のセル（vLLM AWQの並行数4）を同じapplyで測り直し、llama.cpp Q4_K_Mとの比較にはその値を使う |

## Consequences

- 所要時間の見込み（推定。本番の実測から）：非劣化の4セル 約4時間、Q4_K_Mの容量の6セル 約4.5時間、個体差の1セル 約22分、準備（Q4_K_Mの作成を含む）約40分で、
  合計 約9.5時間。自動シャットダウンは720分にする。費用は約$11。
- 結果がどう出ても、追加のapplyは要らないように規則を決めた（示せなかったら件数を足さない、同じ台数なら並べる、個体差は報告するだけ）。
  もう1回要るのは、Q4_K_Mの作成・起動の失敗や時間切れなど、運用の失敗のときだけである。
- 実装：`gguf-q4_k_m`の量子化の値をschemaとセル一覧の検証に足す。`setup.sh`でQ4_K_Mを作る。`make_main_cells.py`で一覧を作る。コードの変更なのでPRにする。
- 示せる確率は約6割で、示せなかった場合は4bitを選べない。それでも「目立った劣化は無かったが、基準では示せなかった」と書く。「劣化した」とは書かない。
- 言える結論は「L4・Qwen3-8B・このワークロード（Tool RAG、入力約2,200トークン）で、実務で選べる4構成の中から選ぶ」に限られる。
  Q4_K_M以外のGGUFの量子化や、AWQ以外の4bitは測らない。
- 並行数の目標を先に決めなかったのは設計の穴だった。台数の表で示すことで、目標が決まれば読めるようにする。

## 追記（2026-10-26）：台数の表の読み方を、Q4_K_Mの速さの判定を見る前に決める

本番3回目の途中（Q4_K_Mの速さの判定を計算する前）に、3節の「構成の選び方」で、判定の結果の読み方が決まっていない所が見つかった。
ここで固定する。この時点で分かっていたのは、Q4_K_Mの容量のセルが並行数32まで起動して容量に収まったことだけで、どのセルが会話用の基準を満たすかは見ていない。

| 決まっていなかったこと | 決定 |
| --- | --- |
| ADR-0003の3値のうち「判定不能」の扱い | 「満たす」だけを数える。判定不能は、満たすと示せていないので数えない |
| 並行数を上げると判定が良くなる場合（例：2が判定不能、4が満たす） | 並行数1から順に見て、「満たす」が途切れる手前までを最大の並行数にする |
| 台数の出し方 | 目標の並行数 ÷ 最大の並行数（切り上げ）。並行数1も満たさない構成は「この基準では出せない」とし、台数を出さない |
| 目標の並行数ごとに、最少の構成が違う場合 | 目標の並行数ごとに選ぶ。行ごとに答えが違えば、そのまま表で示し、1つにまとめない |
| 台数の表の行 | 1・2・4・8・16・**32**。測った範囲（ADR-0003で各エンジン32まで倍々）に揃える。16で止める理由は書かれていなかった |

- 32の行でも、台数は全構成について出す（最大の並行数が4なら8台）。並行数32を起動できなかった構成も、表から抜けない。
- 量子化の非劣化は並行数1で確かめただけで、並行数を上げたときの4bitの精度は確かめていない。限界として書く。

| 懸念 | 対処 |
| --- | --- |
| Q4_K_Mが32まで起動したのを見てから、32の行を足している | 足したのは速さの判定を見る前。台数は全構成について同じ式で出すので、32を起動できたことだけでは有利にならない。32の行で差がつくのは、どれかの構成が並行数32で基準を満たす場合だけである |
| 判定不能を数えないと、厳しすぎる判定になりうる | 判定不能は、1,000件で基準を満たすと示せなかったという結果。数えると、示せていない容量で台数を減らすことになる |

## 追記（2026-10-26）：本番3回目の結果と、基準セルの判定が変わったときの扱い

### 非劣化の判定（`scripts/noninferiority.py`）

| エンジン | selection（bf16 → 4bit） | 差 | 片側99.5%の下限 | p_d / ρ | 判定 |
| --- | --- | --- | --- | --- | --- |
| vLLM（AWQ） | 0.934 → 0.928 | −0.6pt | −2.48pt | 4.6% / 0.15（確かめた範囲内） | **非劣化を示せた** |
| llama.cpp（Q4_K_M） | 0.935 → 0.915 | −2.0pt | −4.05pt | 4.0% / 0.19（p_dが範囲外） | **示せなかった** |

- llama.cppは、下限がマージンを下回り、p_dも4.5%未満で、どちらの理由でも「示せなかった」。「劣化した」とは書かない。
- arg_exact（判定に使わない）：vLLM 0.986 → 0.984、llama.cpp 0.986 → 0.985。

### llama.cpp Q4_K_Mの速さ（会話用の基準、各1,000件）

| 並行数 | 1 | 2 | 4 | 8 | 16 | 32 |
| --- | --- | --- | --- | --- | --- | --- |
| 超過 | 0 | 27 | 769 | 963 | 999 | 1,000 |
| 判定 | 満たす | 満たさない | 満たさない | 満たさない | 満たさない | 満たさない |
| TPOT p50（ms） | 22.5 | 50.9 | 109.3 | 218.6 | 425.0 | 889.8 |

最大の並行数は1。bf16（並行数1のTPOT p50 60.9ms）よりトークンごとの間隔は短いが、並行数2で基準を超える件数が増える。

### 基準セル（vLLM AWQの並行数4）の判定が変わった

| | 本番1回目 | 本番3回目 |
| --- | --- | --- |
| 超過 / 判定 | 2/1,000、上限0.63%、満たす | 59/1,000、上限7.28%、**満たさない** |
| TPOT p50 / p99（ms） | 70.2 / 97.9 | 76.5 / 108.1 |
| SMクロックの中央値（セルの計測区間） | 1,080MHz | 945MHz |
| 電力の中央値 / 温度の最大 | 71.7W / 84℃ | 71.1W / 83℃ |

同じ電力の上限の下でクロックが約12%低く、インスタンスの個体差と見る。決まり（1節）どおり測り直しはしない。
