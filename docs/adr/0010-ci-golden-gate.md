# ADR-0010: CIの回帰ゲートを、保存済みの8Bの答えに対するゴールデンテストにする

- Status: Accepted
- Date: 2026-11-03

## 結論（Summary）

- モデルとエンジン以外のハーネスの部分（並び順・リクエストの組み立て・読み取り・採点）が劣化していないことを、PRごとに確かめる。CIはモデルを動かさず、本番で保存した8Bの答え（5エンジン×1,000件）を使って全件を照合する（5）。
- 1件でも違えば失敗。統計的な判定は使わない。コードとデータが同じなら結果は決まるので、違いはすべてコードの変化による（5）。
- 意図した変更なら、同じPRで期待値を作り直し、変わった件と理由をPRに書く（5）。
- 送る中身を意図して変える変更と、モデル・エンジン・版・量子化の差し替えは、このゲートの対象外。GPUで答えさせて測り直し、ADR-0008・0009の非劣化の判定で決める（5）。
- ADR-0001を置き換える。

## 背景と問い（Context and Problem Statement）

ADR-0001（2026-08-08）は、PRごとにスモーク15件をモデルで流し、selection ≥ 0.85とmainからの低下 −0.05以内をゲートにする案だった。実装しないまま、次の問題が分かった。

- 15件では1件で6.7ptになり、−0.05は1件の入れ替わりで必ず割る。許す幅として働かない。
- −0.05（5pt）は、ADR-0002が「±5ptは緩すぎる」として採らなかった値で、−2.6ptのマージンと食い違う。
- GitHubの標準のランナーにはGPUが無い。CPUで小さいモデル（Qwen3-0.6B Q8_0、llama.cpp b11434、4スレッド）を流すと、1件約33秒で、200件に約1.8時間かかった（2026-11-03、手元のRyzen 5 7520Uでの実測）。

本番の測定は終わり、エンジンのイメージ（ADR-0006）とモデルの重みは固定されている。今後のPRで起きるのは、主に採点・読み取り・スクリプトの手直しで、モデルの答えは変わらない。問いは、**その変更が、固定した入力に対する結果を変えていないことを、どう確かめるか**である。

## 判断の基準（Decision Drivers）

- 全200件を対象にする（15件のような抜き出しで粗くしない）。
- 判定が決まっている（同じコードなら毎回同じ結果）。
- 照合の正解は、できるだけ過去の実際の記録に結びつける（今のコードで作った値を、今のコードで確かめるだけにしない）。
- GPUの費用をかけない。

## 検討した案（Considered Options）

| 案 | 採否 | 理由 |
| --- | --- | --- |
| A. ADR-0001のまま（15件・モデルで流す・−0.05） | 不採用 | 15件では許す幅が働かない。ADR-0002のマージンと食い違う。GPUが要る |
| B. CPUで0.6Bを流し、mainと1件ずつ比べる | 不採用 | 200件で約1.8時間（推定でランナーでも1時間前後）。別の機械では答えが同じになるか確かめていない。0.6Bの変化が8Bの変化を表すかも分からない |
| C. Bに加え、わざと壊した版を0.6Bと8Bで流し、反応が対応するかを確かめる | 不採用 | GPU 1回（約$4、推定）を使っても、次の判断が変わらない。壊した版の数では「代わりになる」とまでは示せない |
| D. 結果の差に非劣化の判定（下限 −2.6pt）を当てる | 不採用 | 結果が決まっているので、差は揺れではない。200件では正解→誤りの件数の閾値と同じになり、加えるものが無い。−2.6ptは8Bの尺度の値で、0.6Bに当てる根拠も無い |
| E. ゲートを作らず、ADR-0001を取り下げる | 不採用 | 筋は通るが、作り直しで壊れていないことを、PRごとに無料で確かめる手段が無くなる |
| F. 保存済みの8Bの答えとリクエストに対するゴールデンテスト | **採用** | 全件・決まった判定・過去の記録との照合・GPU不要を満たす |

## 決定（Decision Outcome）

既存のpytest（`.github/workflows/test.yml`、PRとmainへのpushで動く）に、次の照合を足す。

| # | 照合（処理の順） | 入力 | 正解 | 正解の出どころ |
| --- | --- | --- | --- | --- |
| G1 | ツールの並び順 | ケース・試行の番号・`seed_base` | 記録にある並び順（`tool_order`） | 本番の記録そのもの |
| G2 | 送るリクエスト | 200件×試行5回の、各エンジンのリクエストの本体（OpenAI互換の4エンジンは`build_payload`、transformersはチャットテンプレートと`generate()`に渡す入力） | スナップショット（本体のsha256と、ツール定義を名前に置き換えた要約） | 採用時のmainで作る（本番では本体を記録していない） |
| G3 | 答えの読み取り（パーサー） | 保存した生の答え（`raw_output`） | 記録にある読み取り結果（`decoded`） | 本番の記録そのもの |
| G4 | 採点 | 記録にある読み取り結果 | ケースごとのselection・arg_exact・e2e（期待値ファイル） | 採用時のmainで作る。集計値がmanifestの`selection_mean`と一致することを、作るときに確かめる |

```text
ケース → [G1 並び順] → [G2 リクエスト] → （エンジン・モデル：CIでは動かさない。本番の答えを使う） → [G3 読み取り] → [G4 採点] → 点数
```

対象のセルは、エンジンごとにbf16の普通の精度の測定を1つずつ（5セル）：transformers・llama.cpp・vLLM（第1段階の本番2）、SGLang・TensorRT-LLM（第2段階の本番）。出どころはRelease `runs-2026-10`。

ゴールデンのファイルは`scripts/update_golden.py`で作り、`tests/golden/`に置く（合計約760KB）。

```text
本番の生の記録（5セル×1,000件）
   │ ① --from-runs：要る列（case_id・trial・tool_order・raw_output・decoded）だけを写す。
   │    今のコードがG1とG3を再現し、採点し直したselectionがmanifestと一致するときだけ写す
   ▼
<engine>.answers.jsonl.gz   入力。本番の記録なので、以後は作り直さない
   │ ② 今のコードでリクエストを組み立て、採点する
   ▼
<engine>.expected.jsonl.gz  期待値（G2のリクエスト、G4の採点）。意図した変更のときだけ作り直し、変わった件を一覧に出す
```


判定の読み方：

| 結果 | 読み方 |
| --- | --- |
| G1〜G4がすべて一致 | 通る |
| G1かG3が1件でも違う | 失敗。本番の記録と食い違うので、意図した変更でも期待値は直さない。直すのはコードの側 |
| G2かG4が1件でも違い、意図していない | 失敗。コードを直す |
| G2かG4が違い、意図した変更 | 同じPRで期待値を作り直し（`scripts/update_golden.py`）、変わった件の一覧と理由をPRの本文に書く。G2が変わる（送る中身が変わる）なら、下の「対象外」に当たる |

このゲートの対象外（GPUで答えさせて測り直す）：

- 送る中身を意図して変える変更（プロンプト、ツール定義、サンプリングのパラメーター）
- モデル・エンジン・版・量子化の差し替え

### 確かめ方（Confirmation）

- 採用時（2026-11-03）に、今のコードで5セル×1,000件を確かめた。G3（読み取り）は5,000件すべて一致、G1（並び順）も5,000件すべて一致。採点し直したselectionは、5セルともmanifestと文書の値と一致した（transformers 0.935、llama.cpp 0.939、vLLM 0.937、SGLang 0.929、TensorRT-LLM 0.934）。
- わざと壊した変更（並び順の式を変える、パラメーターを1つ落とす、読み取りで引数の型を変える、採点で引数を比べなくする）で、G1〜G4がそれぞれ失敗することを、`tests/test_golden.py`に含めた。
- ②を作り直すとバイト列が変わらない（gzipの時刻を0に固定）ことを確かめた。照合は全体で約5秒。

## 影響（Consequences）

- 得るもの：採点・読み取り・並び順・送る中身の退行を、PRごとに全件・無料で、本物の8Bの答えに対して確かめられる。ADR-0001とADR-0002の食い違いが無くなる。
- 失うもの：モデルの振る舞いはCIで確かめない。consistency（何回流しても同じ答えか）もゲートにしない。
- 残る穴：下の表の「残る影響」のうち、なし以外の行。

### 妥当性への脅威（Threats to Validity）

| 懸念 | 対処 | 残る影響 |
| --- | --- | --- |
| G2・G4の期待値は今のコードで作るので、今すでにある誤りを正しいものとして固定する | G1・G3は本番の記録と照合する。G4は集計値を本番のmanifestと照合して作る | G2のリクエストの本体は本番で記録していないので、本番と同じだったことは直接には確かめられない（並び順とパラメーターは、G1と既存のエンジン間の一致テストで確かめている） |
| 送る中身を変える変更で、G2の期待値を作り直すだけで通してしまう | 判定の読み方で、G2が変わる変更は対象外（GPUで測り直す）と決めた | 守るのはPRを書く人の手順で、機械では止めていない |
| transformersは、チャットテンプレートをハーネスの側で当てている | G2はテンプレートを当てる前の入力（メッセージ・ツール・生成の設定）で照合する | テンプレートの当て方（tokenizerの版）の変化は、このゲートでは見えない。版はADR-0006で固定している |
| 5セルでは、エンジンに固有の読み取りの経路の一部しか通らない | エンジンごとに1セルを選んだ。読み取りはエンジンの種類ごとに2系統（Hermesのタグ、OpenAI互換の`tool_calls`）で、どちらも通る | 量子化したセルだけに出る出力の形は含まない |
| 期待値を作り直すときに、変わった件を見落とす | 作り直すスクリプトが、変わった件と前後の値を一覧に出す | ― |

## 参考（More Information）

- ADR-0001（置き換え前）、ADR-0002（マージン）、ADR-0006（版の固定）、ADR-0008・0009（非劣化の判定）
- Release `runs-2026-10`（本番の生の記録）

## 追記（Amendments）

種類：**明確化**＝書き方だけを直した／**規則の追加**＝その規則で判定する結果を見る前に決めた／**結果の後の補完**＝その規則で判定する結果を見た後に決めた（理由を本文に書く）／**適用の記録**＝規則どおりに読んだ結果。結果を見た後に規則そのものを変えるときは、新しいADRを立ててこのADRをSupersededにする。
