# ADR-0004: ケースセットを自前で200件に増やす（正解は機械で作り、クエリはLLMが書く）

- Status: Proposed
- Date: 2026-10-15

## Context

`data/`のケースは14件しかない。この件数は最初のコミット（2026-08-16）から変わっておらず、件数の妥当性は検討していなかった
（[[docs/adr/0003-latency-pass-verdict|ADR-0003]]の追記F）。14件では、次の3つの用途のどれにも足りない。

- **第3パス**（並行化しても精度が落ちないか）：±2.6ptの等価性を言うには、入れ替わりが0件という一番よい場合でも約140件が要る
  （[[docs/adr/0002-equivalence-margin|ADR-0002]]の追記）。
- **精度パスのエンジン間比較**：同じ理由で、「精度を犠牲にしていない」と言えない。
- **latencyパス**：判定の精度には効かないが、14種類のプロンプトでは、ワークロードの代表性に限界がある。

近い公開の評価セットの件数は、次のとおりである。

| 評価セット | 近い部分 | 件数 |
| --- | --- | --- |
| BFCL v3 multiple | 2〜4個の関数から1つを選んで呼ぶ | 200 |
| BFCL v3 simple | 関数1つを呼ぶ | 400 |
| BFCL v3 irrelevance | 呼ぶべきでない場面 | 240 |
| FunctionChat-Bench（Kakao、韓国語）の単発の部分 | 英語以外の言語で、単発のツール呼び出し | 500 |

単発のツール呼び出しの評価では、1つのカテゴリにつき200〜500件が一般的な範囲である。
また、中心極限定理に頼る評価は数百件を下回ると信用できない、という指摘もある（arXiv 2503.01747）。

日本語の評価セットとしては、Nejumi LLMリーダーボード4のBFCL日本語版（2025年8月）がある。ただし、単発のカテゴリは各30件に間引かれており、
英語の汎用APIを翻訳したもので、ライセンスの記載も無い。日本語の業務領域で、提示するツールの数を変えて測れる評価セットは見当たらない。

[Source: User, ケース数の見直し, 2026-10-15]

## Decision

### 1. 自前のセットを200件に増やし、全パスで同じセットを使う

- **200件 = 既存14件 + 新規186件。** いちばん近い公開ベンチマーク（BFCL v3 multiple）と同じ規模で、統計の下限（約140件）を超える。
  後から400〜500件に広げられるように、作り方は手順として残す。
- **件数は「正解の呼び出しが互いに違うケース」で数える。** 同じ正解を言い換えただけのクエリは、互いに結果が似やすく、統計的に独立した件数にならない
  （Miller 2024：まとまりのある問題は、まとまりを単位に誤差を出すべきである）。同じ正解の呼び出し（ツールと引数の値の組）を2回使わない。
- **割り振り**：
  - negative（呼ぶべきでない場面）は、既存の割合（14件中2件、約15%）を保って30件にする（既存2件＋新規28件）。
  - 正例170件は、40個のツールに**各4件以上**を割り振る。残りは、紛らわしいツール群（各モジュールにある集計・推移・検索）に厚めに配る。
    今の正例は帳票・販売・マスタに偏り、在庫・人事は0件なので、この偏りを解消する。
- **ケースセットは、パイロットと本番の前に固定する**（ADR-0003の追記F・条件1）。

### 2. 作り方：正解を先に機械で作り、クエリはLLMが書く

ツール呼び出しのデータを作るときの一般的な型（人が正解の枠組みを決める → LLMで量を増やす → 規則とモデルで検査する → 評価用なら人が確認する）に従う。
APIGen（NeurIPS 2024）と同じく、正解を先に決めてから質問を作る向きにする。

1. **正解の呼び出しをスクリプトで作る**（シード固定）。必須の引数は必ず入れ、任意の引数は確率で入れる。値は、enumからは均等に選び、
   年度は現実的な範囲から選び、コード・伝票番号はツール定義の形式どおりに作り、キーワード・名称は用意した語彙から選ぶ。
   紛らわしいツール（`distractor_tools`）は規則で付ける（同じモジュールのツール、他のモジュールの同じ種類のツール）。
   - **期間は、必要な呼び出しには必ず入れる。** 期間はどのツールでも任意の引数なので、確率1/2で入れると、集計・推移の約半数が期間なしになった
     （「請求書は全部で何件？」のような、全期間の集計）。業務では聞かれない形で、正解に期間が無いとモデルがどの期間を付けても減点されず、期間を読み取れるかも測れない。
     そこで、集計（`aggregate_*`・`aggregate_metric`）と推移（`trend_*`）で期間が引かれなかったものには、別のシードで期間を足す。
     ほかの件の引き方は変えない。人員・在庫・倉庫の集計は「今の人数」のように時点の値として読めるので、期間は任意のままにする。
     この規則は手順2・3の後に足したため、該当した19件はクエリを書き直し（`claude-sonnet-5-5`）、正解を見せない検査をやり直した（`claude-opus-5-5`、19件とも一致）。
     [Source: User, 期間が省略されがちなことの指摘, 2026-10-16]
   - **未処理一覧・承認待ちは、処理の流れがある伝票だけを対象にする。** ツール一覧は、どのモジュールにも同じ種類のツールを置き、
     各ツールでそのモジュールの対象をすべて選べるので、「人員の未処理分」「倉庫の未処理レコード」のような、業務では意味の無い呼び出しが引かれた（3件）。
     これも別のシードの後処理で、人員・在庫・倉庫以外の対象に引き直す。引き直した3件はクエリを書き直し、正解を見せない検査をやり直した（3件とも一致）。
     [Source: User, 無作為抽出の確認中の指摘, 2026-10-16]
   - 規則を後から足してケースを書き直したときは、印と抽出を作り直すが、それまでの無作為抽出の件は（印が付かない限り）抽出に残す。
     確認済みの判断が無駄にならないようにするためで、抽出から外れた件の分だけ新しく引く。
   - **正しい呼び出しが2つある集計は引かない。** 人員・在庫数量・作業時間（勤怠）は、モジュールの集計（`aggregate_hr`・`aggregate_inventory`）でも
     横断の集計（`aggregate_metric`）でも答えられる。正解を1つに決めると、もう一方を選んだ正しい答えが不正解になり、試行ごとにどちらかへ揺れれば、
     入れ替わりの割合が上がって必要な件数も増える（ADR-0002の追記）。これらの組み合わせは4つ目のシードの後処理で引き直す（引き直しでは、
     集計の方法が合計しか無い倉庫も避ける）。
   - 重なりは、正解を見せずに「正しい呼び出しになりうるものをすべて挙げる」検査（`claude-opus-5-5`、全正例161件）で洗い出した
     （`data_build/expand/alternatives_calls.jsonl`）。2つ以上が挙がった7件のうち、集計の重なりは上の規則で引き直し、残りはクエリを直した
     （比較の基準の期間、既存の手作りの3件）。引き直した後の件にも同じ検査をかけ、重なりが残っていないことを確かめた。
     [Source: User, ツール構成の重なりの解消, 2026-10-16]
2. **クエリをLLMが書く。** 規則は次のとおり。
   - 正解の引数は、全部クエリに書かれていること。採点は正解にある引数だけを見るので（`score_arg_exact`）、余分な任意の引数は減点されない。
   - enumの値は、英語の識別子ではなく自然な日本語で表すこと。
   - 正解に無い条件は書かないこと。
   - 口調はばらつかせ、2割程度は遠回しな言い方や否定（「個別じゃなくて合計で」）を使った難しい書き方にすること。
3. **機械的に検査する。**
   - 規則：既存の`validate_case_against_tools`で、ツール名と引数の形を検査する。
   - モデル：正解を見せずに、クエリとツールの一覧だけから呼び出しを当てさせ、正解と食い違ったものに印を付ける。
     これはモデルの評価ではなく、「このクエリを読めば正解が1つに決まるか」というケースの校正である。
   - ほぼ同じクエリを検出する。
4. **人が確認する。** 印の付いた件は全件、印の付かなかった件からは無作為に50件を確認する。判断は「そのまま・直す・捨てる」の3つ。
   - **直す**ときは、クエリを書き直し、必要なら正解も、書き直したクエリから1つに決まる呼び出しに直す
     （例：クエリに「前年度」と書いたので、正解に期間`last_fiscal_year`を足す）。
   - 直した件は、正解を見せない検査をやり直し、直した正解と一致することを確かめる（`scripts/build_generated_cases.py`が一致しない件を拒否する）。
     クエリだけから正解が決まることを、人の判断ではなく検査で確かめるためである。
   - 何を直したかを`generation.human_edit`（`none`・`query`・`query_and_gold`）に残し、読み手が人の手の入った件を除いて計算し直せるようにする。

   [Source: User, 正解を人が直してよいかの判断, 2026-10-15]
5. negativeは、業務の文脈でありそうだが、どのツールにも当たらない依頼として別に作る。検査では「どのツールも呼ばない」が正解になる。

### 3. モデルの分担

- **クエリを書くモデル：Claude Sonnet**（`claude-sonnet-5-5`）。量の多い作業なので、速くて安いモデルにする。
- **検査するモデル：Claude Opus**（`claude-opus-5-5`）。強いモデルでも正解を当てられないなら、問題の方が悪い可能性が高い、という論理なので、検査は強い方にする。
- どちらも評価対象（Qwen系）ではない（READMEのデータの透明性ルール3）。書く側と検査する側を別のモデルにして、同じモデルの癖で見逃す可能性を下げる。

### 4. `provenance`に`generated`を加える

正解は機械で作り、クエリはLLMが書いたケースを`generated`とする。既存の`seed_manual`・`grounded`・`adversarial_manual`と区別し、
読み手が作り方ごとに数値を除外して計算し直せるようにする（READMEのデータの透明性ルール1）。
LLMはクエリの文だけを書き、正解の値には触れない（同ルール2）。人が正解を直した件は`generation.human_edit`で区別する（2の手順4）。

## 検討した案

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 14件のまま | 却下 | どの用途にも足りない（Context） |
| BFCLを借りて、精度パスと第3パスに使う | 却下 | Apache 2.0で使え、件数がすぐ足り、ADR-0002のマージンと尺度がそろう利点はある。しかし、ツール数の段階（10・50・100）とlatencyパスには使えないので、2つのセットを保守することになる。パスによってデータが違うと、結論を同じワークロードの上で読めない。英語の汎用APIなので、日本語の業務領域という対象からも外れる |
| Nejumi BFCL日本語版を使う | 却下 | 単発のカテゴリが各30件で足りない。ライセンスの記載が無い |
| 約140件（統計の下限） | 却下 | 一般的な規模（200〜500件）に届かない |
| 400〜500件 | 保留 | 作る手間が2倍以上。200件で手順を確かめてから判断する |
| **自前のセットを200件に増やす（採用）** | 採用 | 全パスが同じケースで測られる。いちばん近い公開ベンチマークと同じ規模で、統計の下限を超える |
| 言い換えで件数を増やす | 却下 | 同じ正解の言い換えは独立した件数にならない |
| 人の確認で正解を一切変えない（直せない件は捨てるか、スクリプトで引き直す） | 却下（ユーザー判断） | 正解がすべてシード固定のスクリプトから出る、という説明は単純になる。しかし、正しい方向に直せる件まで捨てることになる |
| 正解は、クエリに書いた条件を引数として足す場合だけ直せる | 却下（ユーザー判断） | 正解が検査モデルの答えに寄るのを防ぐ狙いだったが、直した件は検査をやり直し、`human_edit`で除いて計算し直せるので、値の変更まで禁じる必要はない |
| 新規186件を全件、人が確認する | 却下（ユーザー判断） | 評価セットの慣行（Nejumi BFCL日本語版は全件を人手で確認）ではあるが、手間に対して、印の付いた件＋抽出で残る不備の上限を示せれば足りると判断した |

## Consequences

- **確認していない件の不備**：印の付かなかった件のうち、抽出した50件以外は人が見ていない。50件の不備の数から、残りの不備の割合の上限を
  Clopper-Pearsonで出して記録する（例：50件に不備が0件なら、95%の確からしさで約6%以下）。
- **検査の独立性**：書く側と検査する側は別のモデルだが、どちらもClaudeなので完全に独立ではない。同じ系統のモデルが共通して見逃す不備は、人の確認でしか拾えない。
- **作り方による違い**：`generated`の正解は機械的に選んだ値なので、実際の業務の問い合わせの分布（どのツールがよく使われるか、どの値がよく出るか）は反映していない。
  ツールごとの件数をそろえたのは、偏りを避けるためで、本番の頻度を再現するためではない。
- **ツール一覧の人工的な部分**：このADRではツール一覧を変えない。人の確認で、一覧そのものに次の不自然さがあると分かった。
  - どのモジュールにも同じ5種類（検索・明細・集計・推移・未処理一覧）を置き、対象を機械的に掛け合わせている。意味の無い組み合わせは正解の作り方の規則で避けた（上の手順1）が、
    ツールの側では選べるままである。
  - 「未処理」は検索の引数ではなく、別のツール（`list_open_*`）で表す。検索の`status`には「未処理」が無い。現実のAPIなら検索の状態の1つにすることも多く、
    ここでの選び分けは、ツールの説明を読んで役割の違いを見分けられるかの試験になっている。
  - 名前・キーワードは自由記述の引数で、あらかじめ決めた分類から選ぶ形ではない。
  一覧を見直す場合は、既存の14件・100ツールの拡張一覧・Article1の前提に及ぶので、別のADRで決める。
  [Source: User, ツールの切り分けへの指摘, 2026-10-16]
- **同じ領域に似たツールを並べることの根拠**：同じ業務領域で役割の近いツールを並べる作りは、次の公開データ・ベンチマークと同じ方向である。
  一方で、どのモジュールにも同じ種類を一律に置く今の一覧は、これらより規則的で、紛らわしさを強めた条件にあたる。
  - τ-bench（retail）：1つの小売領域のツールが、注文の状態で分かれる（保留中の注文はキャンセル・変更、配達済みの注文は返品・交換。ポリシー文書に明記）。
  - BFCL v3 live_multiple（利用者が投稿した実際のツール定義、1,053件）：84%の件で、候補に名前の接頭辞が共通するツールがある
    （例：映画の検索・上映時刻・チケット購入）。接頭辞が共通するかどうかでの大まかな集計である。
  - MetaTool（ICLR 2024）：選択の課題の1つ「似た選択肢」は、埋め込みの類似度で正解に近いツールを候補にしている。
  - なお、BFCL v3 multiple（合成、200件）の候補は、ほとんどが無関係な分野の寄せ集めで（接頭辞が共通するのは50件）、この根拠にはならない。
  [Source: Claude調べ（τ-benchのリポジトリ、BFCLのデータを取得して集計、MetaToolの論文）, 2026-10-16]
- **既存の手作りの件の修正**：全正例の検査で、既存の3件（case_0001・0202・0204）のクエリが、正解を1つに決めていなかった
  （「取引先」が仕入先か顧客か、「売上」が受注か請求か、「購買」だけで伝票の種類が決まらない）。Article1にはまだ実測の数字が無いので、
  クエリを「仕入先マスタ」「受注金額」「発注で」に直した。正解は変えていない。直した文は正解を見せない検査で一致した。
- **Article1との関係**：既存の14件は（上の3件のクエリを除いて）そのまま残し、ツールのカタログも変えない。正解率は測った問題によって変わるので、
  14件で測った数字と200件で測った数字は、そのまま比べられない。ただし、Article1には今のところ実測の数字が無い
  （構成案は数値なしで完結する形で、実測は後から差し込む）。後から数字を入れるときも200件のセットで測れば、Article1とArticle2の数字は同じ問題の上で比べられる。
  作り方ごとの内訳は、常に併記する。
- **READMEの表現**：「評価セットが皆無」は、Nejumi BFCL日本語版があるので言い過ぎになった。範囲を絞った表現に直す（別の変更で行う）。
- schemaの`provenance`のenumに`generated`を加えるので、コードの変更としてPRで行う。
