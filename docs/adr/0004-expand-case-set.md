# ADR-0004: ケースセットを自前で200件に増やす（正解は機械で作り、クエリはLLMが書く）

- Status: Accepted
- Date: 2026-10-15（Accepted 2026-10-16）

## 結論（Summary）

- 評価セットを自前で200件（既存14件＋新規186件、うちツールを呼ぶべきでない30件）に増やし、全パスで同じセットを使う。
- 正解の呼び出しをスクリプトが固定シードで先に作り、LLMはクエリ文だけを書く。正解を見せない別のモデルの検査と、全件の人の確認を通す。
- 正例は40個のツールに各4件以上を割り振り、同じ正解の呼び出しを2回使わない。
- 正解ラベル2件とツールの説明1つは、本番の前に直した（追記2026-10-19）。

## 背景と問い（Context and Problem Statement）

`data/`のケースは14件しかない。この件数は最初のコミット（2026-08-16）から変わっておらず、件数の妥当性は検討していなかった
（[ADR-0003](0003-latency-pass-verdict.md)<!-- gbrain: [[docs/adr/0003-latency-pass-verdict|ADR-0003]] -->の追記F）。14件では、次の3つの用途のどれにも足りない。

- **第3パス**（並行化しても精度が落ちないか）：±2.6ptの等価性を言うには、入れ替わりが0件という一番よい場合でも約140件が要る
  （[ADR-0002](0002-equivalence-margin.md)<!-- gbrain: [[docs/adr/0002-equivalence-margin|ADR-0002]] -->の追記）。
- **精度パスのエンジン間比較**：同じ理由で、「精度を犠牲にしていない」と言えない。
- **latencyパス**：判定の精度には効かないが、14種類のプロンプトでは、ワークロードの代表性に限界がある。

近い公開の評価セットの件数は、次のとおりである。

| 評価セット | 近い部分 | 件数 |
| --- | --- | --- |
| BFCL v3 multiple | 2〜4個の関数から1つを選んで呼ぶ | 200 |
| BFCL v3 simple | 関数1つを呼ぶ | 400 |
| BFCL v3 irrelevance | 呼ぶべきでない場面 | 240 |
| FunctionChat-Bench（Kakao、韓国語）の単発の部分 | 英語以外の言語で、単発のツール呼び出し | 500 |

単発のツール呼び出しの評価では、1つのカテゴリにつき200〜500件が一般的な範囲である。
また、中心極限定理に頼る評価は数百件を下回ると信用できない、という指摘もある（arXiv 2503.01747）。

日本語の評価セットとしては、Nejumi LLMリーダーボード4のBFCL日本語版（2025年8月）がある。ただし、単発のカテゴリは各30件に間引かれており、
英語の汎用APIを翻訳したもので、ライセンスの記載も無い。日本語の業務領域で、提示するツールの数を変えて測れる評価セットは見当たらない。

（決定日 2026-10-15）<!-- gbrain: [Source: User, ケース数の見直し, 2026-10-15] -->

## 決定（Decision Outcome）

### 1. 自前のセットを200件に増やし、全パスで同じセットを使う

- **200件 = 既存14件 + 新規186件。** いちばん近い公開ベンチマーク（BFCL v3 multiple）と同じ規模で、統計の下限（約140件）を超える。
  後から400〜500件に広げられるように、作り方は手順として残す。
- **件数は「正解の呼び出しが互いに違うケース」で数える。** 同じ正解を言い換えただけのクエリは、互いに結果が似やすく、統計的に独立した件数にならない
  （Miller 2024：まとまりのある問題は、まとまりを単位に誤差を出すべきである）。同じ正解の呼び出し（ツールと引数の値の組）を2回使わない。
- **割り振り**：
  - negative（呼ぶべきでない場面）は、既存の割合（14件中2件、約15%）を保って30件にする（既存2件＋新規28件）。
  - 正例170件は、40個のツールに**各4件以上**を割り振る。残りは、紛らわしいツール群（各モジュールにある集計・推移・検索）に厚めに配る。
    今の正例は帳票・販売・マスタに偏り、在庫・人事は0件なので、この偏りを解消する。
- **ケースセットは、パイロットと本番の前に固定する**（ADR-0003の追記F・条件1）。

### 2. 作り方：正解を先に機械で作り、クエリはLLMが書く

ツール呼び出しのデータを作るときの一般的な型（人が正解の枠組みを決める → LLMで量を増やす → 規則とモデルで検査する → 評価用なら人が確認する）に従う。
APIGen（NeurIPS 2024）と同じく、正解を先に決めてから質問を作る向きにする。

1. **正解の呼び出しをスクリプトで作る**（シード固定）。必須の引数は必ず入れ、任意の引数は確率で入れる。値は、enumからは均等に選び、
   年度は現実的な範囲から選び、コード・伝票番号はツール定義の形式どおりに作り、キーワード・名称は用意した語彙から選ぶ。
   紛らわしいツール（`distractor_tools`）は規則で付ける（同じモジュールのツール、他のモジュールの同じ種類のツール）。
   - **期間は、必要な呼び出しには必ず入れる。** 期間はどのツールでも任意の引数なので、確率1/2で入れると、集計・推移の約半数が期間なしになった
     （「請求書は全部で何件？」のような、全期間の集計）。業務では聞かれない形で、正解に期間が無いとモデルがどの期間を付けても減点されず、期間を読み取れるかも測れない。
     そこで、集計（`aggregate_*`・`aggregate_metric`）と推移（`trend_*`）で期間が引かれなかったものには、別のシードで期間を足す。
     ほかの件の引き方は変えない。人員・在庫・倉庫の集計は「今の人数」のように時点の値として読めるので、期間は任意のままにする。
     この規則は手順2・3の後に足したため、該当した19件はクエリを書き直し（`claude-sonnet-5-5`）、正解を見せない検査をやり直した（`claude-opus-5-5`、19件とも一致）。
     （決定日 2026-10-16）<!-- gbrain: [Source: User, 期間が省略されがちなことの指摘, 2026-10-16] -->
   - **未処理一覧・承認待ちは、処理の流れがある伝票だけを対象にする。** ツール一覧は、どのモジュールにも同じ種類のツールを置き、
     各ツールでそのモジュールの対象をすべて選べるので、「人員の未処理分」「倉庫の未処理レコード」のような、業務では意味の無い呼び出しが引かれた（3件）。
     これも別のシードの後処理で、人員・在庫・倉庫以外の対象に引き直す。引き直した3件はクエリを書き直し、正解を見せない検査をやり直した（3件とも一致）。
     （決定日 2026-10-16）<!-- gbrain: [Source: User, 無作為抽出の確認中の指摘, 2026-10-16] -->
   - 規則を後から足してケースを書き直したときは、印と抽出を作り直すが、それまでの無作為抽出の件は（印が付かない限り）抽出に残す。
     確認済みの判断が無駄にならないようにするためで、抽出から外れた件の分だけ新しく引く。
   - **正しい呼び出しが2つある集計は引かない。** 人員・在庫数量・作業時間（勤怠）は、モジュールの集計（`aggregate_hr`・`aggregate_inventory`）でも
     横断の集計（`aggregate_metric`）でも答えられる。正解を1つに決めると、もう一方を選んだ正しい答えが不正解になり、試行ごとにどちらかへ揺れれば、
     入れ替わりの割合が上がって必要な件数も増える（ADR-0002の追記）。これらの組み合わせは4つ目のシードの後処理で引き直す（引き直しでは、
     集計の方法が合計しか無い倉庫も避ける）。
   - 重なりは、正解を見せずに「正しい呼び出しになりうるものをすべて挙げる」検査（`claude-opus-5-5`、全正例161件）で洗い出した
     （`data_build/expand/alternatives_calls.jsonl`）。2つ以上が挙がった7件のうち、集計の重なりは上の規則で引き直し、残りはクエリを直した
     （比較の基準の期間、既存の手作りの3件）。引き直した後の件にも同じ検査をかけ、重なりが残っていないことを確かめた。
     （決定日 2026-10-16）<!-- gbrain: [Source: User, ツール構成の重なりの解消, 2026-10-16] -->
   - **人が捨てた件は、捨てた理由を規則にして、同じIDで引き直す。** 捨てたままにすると件数が減り、ツールごとに4件以上という割り振りも崩れる
     （`search_report`が2件まで減った）。理由が「業務として意味が無い組み合わせ」なら、規則にして5つ目のシードの後処理で引き直す：
     原価センタ・倉庫の合計、倉庫の推移、全品目の在庫数量の推移（品目ごとに単位が違う）、何を調べるかの無い帳票の検索。
     理由がクエリの日本語だけなら、正解はそのままクエリを書き直す。引き直した件と書き直した件は、ほかに正しい呼び出しが無いかの検査をやり直し、人がもう一度確認する。
     これで件数は200件に戻る。
   - クエリを書くモデルへの対応表では、`report_type`の`law`を「法律」とする。「法令」は法律と例規（`ordinance`）の両方を指し、正解が1つに決まらなかった。
     （決定日 2026-10-16）<!-- gbrain: [Source: User, 補充と捨てた件の扱い, 2026-10-16] -->
   - **実際の質問らしくない呼び出しは引かない**（6つ目のシードの後処理）。伝票の無い対象（勘定残高・原価センタ・人員・在庫・倉庫）に伝票番号で明細を引く呼び出し、
     起点の無い階層の深さ、コードでのマスタ照会。人はマスタを名前で尋ねるので、`search_master`は名前で引く（コードを併記すると、コードだけの呼び出しも
     同じく正しくなる。どちらも無ければ何を引くか決まらない）。コードが必須のツール（変更履歴・階層の起点）は残し、クエリでは「社員番号」「品番」
     「仕入先コード」のように番号の種類を書く。伝票番号で照会する件（受注・請求書・入荷など）は、問い合わせや画面の番号を写して尋ねる実務どおりとして残す。
     名前からコードを引いて次を呼ぶ2段の呼び出しは、このベンチの範囲（単発の呼び出し）の外である。
     （決定日 2026-10-16）<!-- gbrain: [Source: User, 全件確認中の指摘（コードで質問することはほとんどない）, 2026-10-16] -->
   - 正解に無い条件がクエリに書かれていても、採点は正解に無い引数を見ないので、正解を見せない検査では見つからない。クエリを書くモデルが
     正解に無い「明細は不要」を足した例があったため、検査の呼び出しが正解より多くの引数を持つ件を洗い出した（今の件には無かった）。
   - **承認待ちは、承認の流れがある伝票と、その伝票が通る段階だけを引く**（7つ目のシードの後処理）。入荷・出荷には承認の流れが無く、
     予算確認は発注の段階で、仕入先からの請求書の段階ではない。対応は`APPROVAL_STAGES`に置く。
   - **検索のキーワードは、対象に合う語だけを使う**（8つ目のシードの後処理、キーワードだけを置き換える）。語彙がモジュール単位だったため、
     勤怠を「評価面談」で探すような組み合わせが出た。語彙を対象単位（`KEYWORDS_BY_ENTITY`）にし、状態を表す語（「移動中」など）は、
     状態の引数と矛盾するので外した。
     （決定日 2026-10-16）<!-- gbrain: [Source: User, 全件確認中の指摘（入荷・出荷に承認は無い、勤怠と評価面談が結びつかない）, 2026-10-16] -->
   - 受注にも承認の流れは無いものとし、販売の承認待ちは請求書だけにする（`APPROVAL_STAGES`から受注を外した。引き直したのは1件で、ほかの件の引き方は変わらない）。
     ツール一覧の`list_pending_sales_approvals`の説明は与信確認・値引承認を例に挙げており、この規則とずれるが、ツール一覧は変えない方針なので制約として残す。
     クエリでは「顧客向けの請求書」と書く。素の「請求書」は仕入先からの請求書とも読め、正解を見せない検査で別解が出たため、確認済みの3件もクエリだけ直した。
   - **人事の推移は、給与の金額を、月か四半期の粒度で、1か月より長い期間について引く**（9つ目のシードの後処理）。給与・勤怠の件数や勤怠の数量の推移は
     業務で見ない。人員は、人数が件数（`count`）と数量（`quantity`）のどちらかをツール一覧が決めておらず、正解が1つに決まらない。給与は月ごとに変わるので、
     日・週の推移には意味が無い。該当した5件を引き直した。
     （決定日 2026-10-16）<!-- gbrain: [Source: User, 全件確認中の指摘（受注に承認は無い、給与・勤怠と件数・数量が結びつかない）, 2026-10-16] -->
2. **クエリをLLMが書く。** 規則は次のとおり。
   - 正解の引数は、全部クエリに書かれていること。採点は正解にある引数だけを見るので（`score_arg_exact`）、余分な任意の引数は減点されない。
   - enumの値は、英語の識別子ではなく自然な日本語で表すこと。
   - 正解に無い条件は書かないこと。
   - 口調はばらつかせ、2割程度は遠回しな言い方や否定（「個別じゃなくて合計で」）を使った難しい書き方にすること。
3. **機械的に検査する。**
   - 規則：既存の`validate_case_against_tools`で、ツール名と引数の形を検査する。
   - モデル：正解を見せずに、クエリとツールの一覧だけから呼び出しを当てさせ、正解と食い違ったものに印を付ける。
     これはモデルの評価ではなく、「このクエリを読めば正解が1つに決まるか」というケースの校正である。
   - ほぼ同じクエリを検出する。
4. **人が確認する。** 印の付いた件は全件、印の付かなかった件からは無作為に50件を確認する。判断は「そのまま・直す・捨てる」の3つ。
   無作為50件で、正解が1つに決まらない不備が3件あり（1011・1115・1143）、残りの件の不備の割合の上限（Clopper-Pearson片側95%）は約15%と出た。
   評価の正解として確かめたと言える水準ではないので、**残りの件も全件、人が確認する**（`generation.review`は`rest_reviewed`）。
   （決定日 2026-10-16）<!-- gbrain: [Source: User, 無作為抽出の結果を受けて, 2026-10-16] -->
   - **直す**ときは、クエリを書き直し、必要なら正解も、書き直したクエリから1つに決まる呼び出しに直す
     （例：クエリに「前年度」と書いたので、正解に期間`last_fiscal_year`を足す）。
   - 直した件は、正解を見せない検査をやり直し、直した正解と一致することを確かめる（`scripts/build_generated_cases.py`が一致しない件を拒否する）。
     クエリだけから正解が決まることを、人の判断ではなく検査で確かめるためである。
   - 何を直したかを`generation.human_edit`（`none`・`query`・`query_and_gold`）に残し、読み手が人の手の入った件を除いて計算し直せるようにする。

   （決定日 2026-10-15）<!-- gbrain: [Source: User, 正解を人が直してよいかの判断, 2026-10-15] -->
5. negativeは、業務の文脈でありそうだが、どのツールにも当たらない依頼として別に作る。検査では「どのツールも呼ばない」が正解になる。

### 3. モデルの分担

- **クエリを書くモデル：Claude Sonnet**（`claude-sonnet-5-5`）。量の多い作業なので、速くて安いモデルにする。
- **検査するモデル：Claude Opus**（`claude-opus-5-5`）。強いモデルでも正解を当てられないなら、問題の方が悪い可能性が高い、という論理なので、検査は強い方にする。
- どちらも評価対象（Qwen系）ではない（READMEのデータの透明性ルール3）。書く側と検査する側を別のモデルにして、同じモデルの癖で見逃す可能性を下げる。

### 4. `provenance`に`generated`を加える

正解は機械で作り、クエリはLLMが書いたケースを`generated`とする。既存の`seed_manual`・`grounded`・`adversarial_manual`と区別し、
読み手が作り方ごとに数値を除外して計算し直せるようにする（READMEのデータの透明性ルール1）。
LLMはクエリの文だけを書き、正解の値には触れない（同ルール2）。人が正解を直した件は`generation.human_edit`で区別する（2の手順4）。

## 影響（Consequences）

- **できたもの**：`data/generated/generated.jsonl`の186件（正例158件・negative 28件）。既存の14件と合わせて200件（negative 30件）。
  人の確認は186件すべて（印あり29件・無作為50件・残り107件）。人の手が入った件は21件（クエリのみ15件・クエリと正解6件、`generation.human_edit`）。
  `scripts/build_generated_cases.py`は、判断の無い件が1件でもあれば書き出さない。
- **人の確認の範囲**：全件を人が確認するので、抽出からの上限の推定は、全件確認に切り替えた理由としてだけ使う（手順4）。
  人は1人なので、確認した人の見落としは残りうる。
- **検査の独立性**：書く側と検査する側は別のモデルだが、どちらもClaudeなので完全に独立ではない。同じ系統のモデルが共通して見逃す不備は、人の確認でしか拾えない。
- **作り方による違い**：`generated`の正解は機械的に選んだ値なので、実際の業務の問い合わせの分布（どのツールがよく使われるか、どの値がよく出るか）は反映していない。
  ツールごとの件数をそろえたのは、偏りを避けるためで、本番の頻度を再現するためではない。
- **ツール一覧の人工的な部分**：このADRではツール一覧を変えない。人の確認で、一覧そのものに次の不自然さがあると分かった。
  - どのモジュールにも同じ5種類（検索・明細・集計・推移・未処理一覧）を置き、対象を機械的に掛け合わせている。意味の無い組み合わせは正解の作り方の規則で避けた（上の手順1）が、
    ツールの側では選べるままである。
  - 「未処理」は検索の引数ではなく、別のツール（`list_open_*`）で表す。検索の`status`には「未処理」が無い。現実のAPIなら検索の状態の1つにすることも多く、
    ここでの選び分けは、ツールの説明を読んで役割の違いを見分けられるかの試験になっている。
  - 名前・キーワードは自由記述の引数で、あらかじめ決めた分類から選ぶ形ではない。
  一覧を見直す場合は、既存の14件・100ツールの拡張一覧に及ぶので、別のADRで決める。
  （決定日 2026-10-16）<!-- gbrain: [Source: User, ツールの切り分けへの指摘, 2026-10-16] -->
- **同じ領域に似たツールを並べることの根拠**：同じ業務領域で役割の近いツールを並べる作りは、次の公開データ・ベンチマークと同じ方向である。
  一方で、どのモジュールにも同じ種類を一律に置く今の一覧は、これらより規則的で、紛らわしさを強めた条件にあたる。
  - τ-bench（retail）：1つの小売領域のツールが、注文の状態で分かれる（保留中の注文はキャンセル・変更、配達済みの注文は返品・交換。ポリシー文書に明記）。
  - BFCL v3 live_multiple（利用者が投稿した実際のツール定義、1,053件）：84%の件で、候補に名前の接頭辞が共通するツールがある
    （例：映画の検索・上映時刻・チケット購入）。接頭辞が共通するかどうかでの大まかな集計である。
  - MetaTool（ICLR 2024）：選択の課題の1つ「似た選択肢」は、埋め込みの類似度で正解に近いツールを候補にしている。
  - なお、BFCL v3 multiple（合成、200件）の候補は、ほとんどが無関係な分野の寄せ集めで（接頭辞が共通するのは50件）、この根拠にはならない。
  （調べた日 2026-10-16。τ-benchのリポジトリ・BFCLのデータを取得して集計し、MetaToolの論文を読んだ）<!-- gbrain: [Source: Claude調べ（τ-benchのリポジトリ、BFCLのデータを取得して集計、MetaToolの論文）, 2026-10-16] -->
- **既存の手作りの件の修正**：全正例の検査で、既存の3件（case_0001・0202・0204）のクエリが、正解を1つに決めていなかった
  （「取引先」が仕入先か顧客か、「売上」が受注か請求か、「購買」だけで伝票の種類が決まらない）。14件で測った数字はまだ公表していないので、
  クエリを「仕入先マスタ」「受注金額」「発注で」に直した。正解は変えていない。直した文は正解を見せない検査で一致した。
- **最初の14件との関係**：既存の14件は（上の3件のクエリを除いて）そのまま残し、ツールのカタログも変えない。正解率は測った問題によって変わるので、
  14件で測った数字と200件で測った数字は、そのまま比べられない。14件で測った数字は公表していないので、数字はすべて200件のセットで測る。
  作り方ごとの内訳は、常に併記する。
- **READMEの表現**：「評価セットが皆無」は、Nejumi BFCL日本語版があるので言い過ぎになった。範囲を絞った表現に直す（別の変更で行う）。

### A1 追記（2026-10-19）：正解ラベル2件とツールの説明1つを直す

1回目のapply（疎通）で、最初の20件のうち2件を、4つの構成がすべて同じように外した。生出力とツールの説明を照らし合わせると、
モデルではなく正解ラベルの側に問題があった（`docs/gpu-smoke-2026-10-18.md`のD4）。

| ケース | クエリ | 問題 | 直し方 |
| --- | --- | --- | --- |
| case_0101 | 2023年度の有価証券報告書から従業員数を調べて | 正解（`search_report`）が`metric: employee_count`と`query_text: 従業員数`の両方を求めていた。`metric`の説明は「定型指標。定型外は query_text のみ使う」で、従業員数は定型の指標なので、`metric`だけを渡すのが説明どおり | 正解から`query_text`を外す。採点は正解に書いたキーしか見ない（`eval_bench/scorers/separated.py`の`score_arg_exact`）ので、`query_text`を足して呼んだ場合も正解になる |
| case_0102 | 有報の従業員数、2020年度から2023年度でどう推移した？ | 正解が`compare_report_metric`だった。`trend_report_metric`の説明は「区間内の推移そのものが必要な場合に使う」で、4年度の推移を聞くこのクエリに合う。一方`compare_report_metric`の説明にも「推移や増減が求められている場合に使う」とあり、説明が重なっていた。200件の中でも、「推移」と言うcase_1152・1154はtrend、「比較」「比べて」と言うcase_1031〜1033はcompareで、case_0102だけが食い違っていた | 正解を`trend_report_metric`に変える。`compare_report_metric`の説明から「推移」を外し、2年度間の差・増減に絞る |

- **case_0102の紛らわしいツール**：正解をtrendに変えるので、`compare_report_metric`を`distractor_tools`の先頭に足す。trendが正解の他のケース（case_1152〜1154）と同じ形にし、
  紛らわしいツールがステージ10の集合に必ず入るようにする。
- **ツールの説明の変更**：`compare_report_metric`の説明を「同一指標を2年度間で比較し、差・増減を返す。単年度の記載値取得や、区間内の各年度の値の並び（trend_report_metric）ではなく、
  2時点の比較が求められている場合に使う。」に変える。`schema/tools.json`（2.1.0→2.1.1）と`schema/tools_extended.json`（ext100-1.1.0→ext100-1.1.1）の両方で変える。カタログの版が変わり、
  プロンプトの長さも変わるので、[ADR-0005](0005-capacity-check.md)<!-- gbrain: [[docs/adr/0005-capacity-check|ADR-0005]] -->の1リクエストの最大は直した後に数え直す。説明の重なりは、「推移」と言う
  case_1152・1154の判定にも効くので、ラベルだけでなく説明も直す。
- **同じ型の問題は、200件の中で他に無かった**（手元で機械的に走査）。定型の指標なのに`query_text`を正解に含める`search_report`のケースはcase_0101だけ、
  compareとtrendが正解の8件で言い回しと正解が食い違うのはcase_0102だけだった。2件とも最初のコミット（2026-08-16）からある手作りの14件にある。
- **直すときの決まり**：モデルが外したケースだけを直すと、正解率が直した分だけ上に偏る。そこで、直すかどうかはモデルの出力ではなく、
  **正解ラベルがツールの説明文と矛盾しているか**で決め、同じ基準を全件に当てる（上の走査）。パイロットで新たな疑いが出たら、同じ基準で本番の前に直し、
  **本番の後は直さない**。今回のきっかけがモデルの出力だったことも、ここに記録しておく。
- **検討した案**

  | 案 | 採否 | 理由 |
  | --- | --- | --- |
  | 200件を全件、人が見直す | 却下 | 同じ型が他に無いと分かったので、今は要らない。他の型の疑いは、パイロットの結果から上の決まりで拾う |
  | 直さない（エンジン間の比較には効かないため） | 却下 | 比較を偏らせなくても、正解ラベルの誤りは精度の水準を一律に下げ、consistencyの解釈も濁す |
  | case_0102はクエリを「比べて」に直し、正解はcompareのまま | 却下 | 手作りの3件をクエリの側で直した前例（Consequences）はあるが、利用者の自然な聞き方に正解を合わせるほうを採る |

- **最初の14件との関係**：14件で測った数字は公表していないので、上の「既存の手作りの件の修正」と同じく、直したセットで測る。
