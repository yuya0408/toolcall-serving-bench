# ADR-0009: 連続バッチングのエンジンどうしを、同じインスタンスで比べる

- Status: Proposed
- Date: 2026-10-27

## Context

本番3回（ADR-0007・ADR-0008）で、`transformers`・`llama.cpp`・`vLLM`の3つを比べ、L4 1台・このワークロード（約2,300トークンを読んで約40トークンを返す）では、
足切りを通った構成のうちvLLM AWQの台数が最も少なかった。3つは「素の実装 → 1リクエスト向けの最適化 → 連続バッチングのサーバー」という系統から
1つずつ選んだもので（計画書、2026-08-29）、**連続バッチングの系統の中の候補は比べていない**。SGLangとTensorRT-LLMは、計画の段階で候補として検討した記録が無い。

このままだと、結論は「系統の間でvLLMが良かった」までで、「連続バッチングのエンジンの中でどれを選ぶか」には答えていない。そこで、連続バッチングのエンジンどうしを比べる。
速さの判定と選び方は第1段階と同じ規則を使い、精度の足切りだけは、エンジンが3つ並ぶこの段階に合わせて決め直す（下の5）。[Source: User, エンジンの候補の見直し, 2026-10-27]

このapplyを最後の測定にするので、エンジンと同じように「検討しないまま決まっていた」選択を見直した。量子化の方式（FP8を検討した記録が無い）と、
負荷のかけ方（ADR-0003の追記2026-10-27）が見つかった。[Source: User, 最後のapplyの前の抜け漏れの見直し, 2026-10-27]

**この段階の問い**：連続バッチングのエンジンと量子化の方式を替えると、足切りを通る構成と、目標の並行数ごとの台数が変わるか。

## 検討した案

### 何を比べるか

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 今の3つのままにし、SGLang・TensorRT-LLMを測っていないことを限界に書く | 却下 | 外した理由を、決めた時点の記録から書けない。後から理由を作ると、結果に合わせた言い訳になる |
| SGLangだけを足す | 却下 | 中立な比較（InferenceX、SemiAnalysis）や比較の記事では、vLLM・SGLang・TensorRT-LLMの3つが並ぶことが多い。TensorRT-LLMだけ外す理由が無い |
| TGIも足す | 却下 | Hugging Faceが2025-12-11から保守だけの状態にし、新しく使うならvLLM・SGLangを勧めている（TGIの文書） |
| LMDeployも足す | 却下 | 下の規則1に当たらない（比較の記事で3つと並ぶことが少ない）。Qwen3のツール呼び出しへの対応も確かめられなかった |
| Triton Inference Server・Dynamo・NIMを足す | 却下 | エンジンではなく、TensorRT-LLMやvLLMを中で動かす配信の層。Ollamaを外した理由（計画書）と同じ |
| SGLang・TensorRT-LLMだけを測り、vLLMは本番1回目の値を使う | 却下 | インスタンスが替わると、vLLM AWQの並行数4の判定が変わった（ADR-0008の追記）。違うインスタンスの値どうしでは、差がエンジンのせいか言えない |
| 各エンジンの設定を詰めてから測る | 却下 | 詰めた量の差が結果に混ざる。第1段階もvLLM・llama.cppとも既定の設定で測った |
| 量子化は4bit（AWQ）だけにする | 却下 | L4はFP8に対応していて、Qwenの公式の`Qwen/Qwen3-8B-FP8`（2025-04公開）もある。FP8を外す理由を書けない |
| FP8を外して費用を下げる（約$34） | 却下 | このapplyが最後の測定なので、後から足せない。差は約$14 |
| ツール一式を固定する構成（プレフィックスキャッシュが効く）のセルも足す | 却下（このプロジェクトでは測らない） | 40個を全部渡すとプロンプトが約8,000トークンで、文脈の長さ（8192）にほぼ届く。全ケースの正解を含む10個の共通の集合は作れず、ツールの集合を作り直すことになる。別のワークロードを測ることになり、約+12時間以上かかる。結論は「ツール定義がリクエストごとに変わる構成（Tool RAG）では」に限る（ADR-0003の追記2026-10-24） |
| 到着の間隔をランダムにする送り方で測り直す | 却下 | 第1段階と比べられなくなる。台数の表は「目標の並行数」で出していて、今の送り方と合っている（ADR-0003の追記2026-10-27） |

### 精度の足切りをどうするか

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 新しいエンジンのbf16は、第1段階と同じく測らずに足切りを通す | 却下 | ツールパーサーなどの違いでエンジンの精度が低くても、量子化の構成は同じエンジンのbf16と比べるので気づけず、速ければ選ばれる |
| 新しいエンジンのbf16を、vLLM bf16に対する非劣化で足切りし、量子化は自分のbf16と比べる（ADR-0008の規則をそのまま重ねる） | 却下 | 2段で許す差が足し合わさり、量子化の構成はvLLM bf16より最大で約5.2pt低くても通り得る。vLLMだけが判定されない基準になり、vLLMに有利 |
| vLLM bf16を、全部の構成の共通の基準にする | 却下 | vLLMだけが判定されない基準になる。vLLM bf16が他の2つより低かったときに気づけない |
| bf16は判定せず、量子化の構成だけを判定する | 却下 | 最初の案と同じく、エンジンの精度の低さに気づけない |
| 2段で判定する（まずbf16どうし、通ったものの中で量子化） | 却下 | 下の5（F）とほぼ同じことを、判定を2回重ねて行う。重ねるぶん誤りの率の見積もりが難しくなる |
| 「害が無いか」（劣っている）を判定し、示せたものだけを外す | 却下 | 件数が少ないと何も外れず、精度の低い構成が通る。第1段階の非劣化（示せたものだけ通す）と向きが逆になる |
| ADR-0008の範囲の規則（p_d ≥ 4.5%、ρ ≤ 0.3）を残す | 却下 | bf16どうしは答えがほぼ一致するので、p_dが4.5%を下回る。範囲の外は「示せなかった」になり、**一致しているほど足切りを通らない**ことになる |
| 範囲の中は99.5%、外は99.9%と、信頼度を切り替える | 却下 | 信頼度をデータで選ぶことになり、範囲の境目の前後で判定が逆転し得る |
| 第1段階の判定も新しい規則でやり直す | 却下 | 第1段階の規則は結果より前に決めた。結果を見た後に変えると、vLLM AWQの判定が「示せた」から「示せなかった」に変わる（99.9%の下限は約−2.86pt）。第1段階はADR-0008のまま残し、第2段階で同じ構成をもう一度判定する |

## Decision

### 1. 候補を選ぶ規則（エンジンの名前ではなく、この規則で選ぶ）

1. 中立な比較（InferenceX）や複数の比較の記事に共通して載っている、連続バッチングのサーバーであること
2. 開発が続いていること（保守だけの状態でない）
3. 第1段階と同じ条件にそろえられること：OpenAI互換のchat/tools API、ストリームでのツール呼び出し、Qwen3のツールパーサー、
   `chat_template_kwargs`で思考を切れる、サンプリングの設定（`temperature`・`top_p`・`top_k`・`seed`）を受け付ける、L4でbf16が動く

1と2で、vLLM・SGLang・TensorRT-LLMが残る。3は疎通のapply（2）で確かめ、そろえられないエンジンは調整せずに除外し、その理由を報告する（計画書の「比較可能性の規律」）。
量子化の構成（AWQ・FP8）が動かないときは、そのエンジンのその構成だけを除外する。

### 2. 疎通のapply（本番の前）

本番のセルを流す前に、短いapply（セル39個で約2.6時間、準備を含めて約4.5時間の見込み）で次を確かめる。結果は`docs/`に記録し、この節の追記にまとめる。
ソースと文書で確かめた事実は`docs/engines.md`にある。

| 確かめること | SGLang 0.5.21 | TensorRT-LLM 1.2.1 |
| --- | --- | --- |
| 版と環境 | torch 2.13.0・transformers 5.12.1を固定で要求する。`~/venv-sglang`に分ける | torch 2.9.1・transformers 4.57.3を要求し、MPIが要る。`~/venv-trtllm`に分ける |
| Qwen3のツールパーサー | `--tool-call-parser qwen`（ソースで確認） | `--tool_parser qwen3`（ソースで確認） |
| AWQのチェックポイント | `Qwen/Qwen3-8B-AWQ`（vLLMと同じ）が読めるか | 読めない（ソースで確認）。ModelOptでINT4 AWQを作る（下の4） |
| FP8のチェックポイント | `Qwen/Qwen3-8B-FP8`（ブロック単位のFP8）が読めて、L4で動くか。vLLMも同じことを確かめる | ブロック単位は対応外（対応表）。ModelOptでテンソル単位のFP8を作る（下の4） |
| FP8の計算が本当にFP8で動くか | 起動のログで、FP8のカーネルが選ばれているか（16bitに戻して計算していないか）。3つのエンジンとも | 同じ |
| `chat_template_kwargs`・`top_k`・`seed` | 受け付けて、効いているか | 同じ |
| ツール呼び出しの答えの形 | 数件で、vLLMと同じ形（名前と引数）で返るか | 同じ |
| 同じ入力か | 同じケースの`usage.prompt_tokens`が、vLLMと同じか（チャットテンプレートの違いが無いか） | 同じ |
| greedyで答えが決まるか | 短い精度のセルを2回回し、答えが一致するか（一致しない割合は、下の5の基準どうしの不一致に入る） | 同じ |
| 容量の判定（ADR-0005） | `/metrics`の`sglang:max_total_num_tokens`が読めるか | `/metrics`の`kvCacheStats`が、短いリクエストを1件送った後に読めるか |
| 回した後の確かめ（ADR-0005） | `sglang:num_retracted_requests_total`が読めるか | 追い出しは起きない（`GUARANTEED_NO_EVICT`）。かわりに、並行数ぶんのリクエストが同時に走っていたか（反復ごとの統計の実行中のリクエスト数）を読めるか |
| 実際に使われた設定 | 起動のログに残るか | 解決された設定（スケジューラの方針、`max_batch_size`、`max_num_tokens`）を起動のログから残せるか |
| ストリームの使用量 | `stream_options.include_usage`、`prompt_tokens_details`（prefix cacheの率） | 同じ |

疎通のセルは、各エンジン×bf16・AWQ・FP8について、短いgreedyのセルを2回と、速さの測定を並行数1と16で短く回す（ADR-0005の容量の判定を通す）。サンプリングの設定はエンジンの側の処理なので、普通の精度の短いセルは各エンジンのbf16だけで回す。

**追記（2026-10-28、疎通の結果）**：9構成がすべて起動して答え、確認表の項目を通った（詳しくは`docs/gpu-smoke-batching-2026-10-28.md`）。
落ちたセルの原因を直し（PR #27〜#29）、同じインスタンスで流し直した。結果を見て決めたことは3つで、どれも構成を除外していない。

| 決めたこと | 中身 | 理由 |
| --- | --- | --- |
| SGLangの`--mem-fraction-static`を0.87に固定 | 自動の0.684ではbf16が起動しなかった。vLLMの既定でbf16が載る並行数8が載る最小の値（0.01刻みで実測）を、全チェックポイントに使う | 2026-10-18の規則（要件を満たすように1エンジンにつき1つの設定を動かしてよい）。下の5の「既定の設定で測る」の例外として記録する |
| SGLangの入力が100トークン長いのは、そのまま測る | SGLangはツールを自分の型に読み込んで書き戻すので、`"strict"`などが足される。容量の判定はSGLangの入力で数えた上限（2,691）を使う | 切り替える設定が無く、こちらで合わせると他のエンジンと第1段階の入力まで変わる。上の1の3にある条件（APIの機能）は満たしている |
| vLLMのFP8が16bitで計算するのは、そのまま測る | vLLM 0.31.0はブロック単位のFP8をL4でMarlin（W8A16）で動かした。SGLang・TensorRT-LLMはFP8で計算した | 下の4の「各エンジンの公式の経路で動くものを使う」。速さの結果に、計算の仕方をエンジンごとに書く |

予想される反論：「入力や計算の仕方が違うなら、同じ条件の比較と言えない」→ 比べているのは「同じ重みを各エンジンの公式の経路で配信したとき」で、
違いはどちらもエンジンの既定の振る舞いから来ている。調整してそろえると、そのエンジンを使う人が実際に得るものではなくなる。違いは結果と一緒に書き、
精度の差がその違いから来た可能性は限界として残す。

### 3. 本番のセル（1回のapply、同じインスタンス）

| 目的 | セル | パス |
| --- | --- | --- |
| 速さ | vLLM・SGLang・TensorRT-LLM × bf16・AWQ・FP8 の9構成 × 並行数 1・2・4・8・16（45セル） | `latency`、1,000件＋ウォームアップ200件（ADR-0003） |
| 普通の精度 | SGLang bf16・TensorRT-LLM bf16（2セル） | `accuracy`、並行数1、200件×5試行 |
| 精度の足切り | 9構成すべて、並行数1（9セル。vLLMのbf16・AWQも測り直す） | `accuracy_under_load`、greedy、200件×5試行、seed_base 0（ADR-0008） |

- **並行数の範囲は9構成でそろえる。** 第1段階で、vLLMはbf16が並行数2、AWQが4までしか満たさなかったが、エンジンの名前で範囲を変えない。
  事前の容量の判定で入らないセルは、第1段階と同じく`unsupported`として記録する。
- **精度の足切りのセルは、vLLMのものも測り直す。** 下の5で3つのbf16を互いの基準にするので、基準も同じインスタンス・同じ版でそろえる（約1.8時間）。
  vLLMの普通の精度（temperature 0.7）は判定に使わないので、本番2回目の値を使う。
- **並び順**：速さのセルを先に、精度のセルを後に回し、それぞれの中を固定のseedでランダムにする（ADR-0007）。一覧は`make_main_cells.py`で作り、手で書き換えない。
  速さのセルを先にするのは、7で、途中で止まったときに測り直す範囲を小さくするため。
- 同時に送ると答えが変わるかの確認（第3パス）は回さない。選定の規則に入っておらず（ADR-0008の3）、第1段階でもどちらの判定もつかなかった。
  第3パスはvLLM・llama.cppでしか測っていないことを、限界に書く。
- **タイムアウトは第1段階と同じ。** 速さの1リクエストは120秒（`run_cell.py --request-timeout`）、精度の1リクエストは600秒、セル全体は見込みの1.5倍（90分以上）。
  TensorRT-LLMは入れないリクエストを列で待たせるので、待った時間もTTFTに入る。容量の判定（ADR-0005）を通ったセルでは、待ちは本来起きない。

### 4. 量子化のそろえ方

- 量子化の構成は、エンジンの間で方式をそろえず、各エンジンの公式の経路で動くものを使う。判定は下の5の通り、3つのbf16に対して行う。
- **AWQ**：`Qwen/Qwen3-8B-AWQ`を読めるエンジン（vLLM・SGLang）は、それを使う。TensorRT-LLM 1.2.1は読み込み処理にAWQの分岐が無いので、
  NVIDIAの公式の量子化の道具（ModelOpt 0.37.0、`hf_ptq.py --qformat int4_awq`）で、同じ`Qwen/Qwen3-8B`から作り、手順とハッシュを記録する。llama.cpp Q4_K_Mを自分で作ったのと同じ扱い。
- **FP8**：`Qwen/Qwen3-8B-FP8`（128×128のブロック単位）を、読めるエンジン（vLLM・SGLang）で使う。TensorRT-LLM 1.2.1はブロック単位のFP8がQwen3でもAdaでも対応外なので、
  ModelOptの`--qformat fp8`（テンソル単位）で作る。NVIDIAが公開している`nvidia/Qwen3-8B-FP8`はKVキャッシュもFP8にしてあるので使わず、`--kv_cache_qformat none`を付けて自分で作る。
  ModelOptの調整用のデータは`hf_ptq.py`の既定（cnn_dailymailの512件）。
- KVキャッシュの量子化（`--kv-cache-dtype fp8`など）は使わない。設定を詰めることに当たり、精度にも効きうる。
- llama.cppのFP8に当たる構成（Q8_0）は測らない。llama.cppは第1段階の系統の比較で、この段階の候補ではない。

### 5. 判定と選び方

- 速さの判定はADR-0003、選び方はADR-0008の3（足切り → 最大の並行数 → 台数が最も少ない構成。同じ台数なら並べて決めない）をそのまま使う。
- **精度の足切り（F案）**：greedy・並行数1の9セル（`scripts/noninferiority.py --batching`）で、次の順に判定する。

| 段 | 判定するもの | 基準 | 通る条件 |
| --- | --- | --- | --- |
| 1 | 各エンジンのbf16 | 他の2つのエンジンのbf16の、(ケース, 試行)ごとの平均。他の2つが通ったかどうかで入れ替えない | 非劣化を示せた |
| 2 | 各エンジンのAWQ・FP8（vLLMを含む） | 段1を通ったbf16の、(ケース, 試行)ごとの平均。自分のbf16が通らなかったときも、同じ基準で判定する | 非劣化を示せた |

- **非劣化の判定**：ケースごとの差（5試行の平均、判定するもの − 基準）の平均に、**片側99.9%のt区間**の下限を付け、下限 > −2.6pt なら「示せた」、それ以外は「示せなかった」。
  マージン（−2.6pt）と指標（selection。arg_exactは報告だけ）はADR-0008と同じ。範囲の規則（p_d・ρ）は置かず、p_dとρは報告だけする。
- **99.9%にした理由**：範囲の規則を置かないので、起こり得るどの不一致の割合でも、誤りの率（本当の差が−2.6ptなのに「示せた」とする割合）が2.5%以下になる信頼度を1つ選ぶ。
  シミュレーション（`scripts/gate_simulation.py`。200件×5試行、各4,000回、正解率0.75、ρ 0〜0.3）で、各信頼度の最悪の誤りの率は次の通り。

| 信頼度 | 99.5% | 99.8% | 99.9% |
| --- | --- | --- | --- |
| 最悪の誤りの率（基準1〜3つ、p_d 0〜12%） | 3.6% | 2.6% | **2.3%** |

  99.9%で、本当の差が0のときに「示せた」となる確率（基準が2つか3つ）：

| 判定するもの | 基準どうしの不一致 p_d | 示せる確率 |
| --- | --- | --- |
| 基準と同じくらい答えが揺れる構成（bf16どうしを想定） | 〜3% | 97%以上 |
| 同上 | 4.5% | 89〜98% |
| 同上 | 6〜8% | 62〜94% |
| 基準の1.5倍揺れる構成 | 基準 4.5%（判定するものは約6.8%） | 79〜90% |
| 基準はほぼ一致し、判定するものだけ揺れる構成（量子化を想定） | 判定するものと基準の不一致 3% | 96%以上 |
| 同上 | 4.5% | 86〜99% |
| 同上 | 6〜8% | 59〜98% |

- **判定の読み方**（結果より前に決める）：

| 場合 | 読み方 |
| --- | --- |
| 3つのbf16とも通った | 量子化の構成は3つの平均と比べる |
| 一部のbf16が通らなかった | そのbf16は足切りを通らない。通ったbf16は、通らなかったbf16を含む基準で判定済みで、やり直さない |
| bf16が1つも通らなかった | どの構成も足切りを通らない。「bf16どうしが一致しない」と報告し、選ばない |
| 疎通でエンジンが外れた | 残ったエンジンのbf16で同じ規則を使う（2つなら互いを基準にする）。vLLMだけが残ったら、vLLM bf16を基準とし、判定せずに通す |
| 量子化の構成と自分のbf16の差 | 報告するだけで、判定に使わない |
| vLLM AWQの判定が第1段階と違った | 両方を報告する。第1段階の結論はADR-0008の規則によるもので、書き換えない |

- 普通の精度（temperature 0.7）は報告し、判定には使わない。
- **台数の表は、この段階のapplyの値だけで作る。** 第1段階のvLLMの値は、参考として並べる。vLLMの判定が第1段階と変わったら報告し、測り直しはしない。
- 既定の設定で測る。radix cache（SGLang）、チャンク単位のプリフィル、KVに割り当てるメモリの割合などは変えない。変えたものがあれば、理由と一緒に記録する（SGLangのメモリの割合だけ変えた。上の2の追記）。
  例外は、vLLMのセルで指定している文脈の長さ（`max_model_len` 8192）で、新しいエンジンも同じ値にそろえる（KVの容量の判定の前提がそろうため）。

### 6. 版の固定

疎通で通しで動いた版を`pins.sh`に固定し、本番はその版で回す（ADR-0006と同じ）。どちらも、公開から2週間以上たった安定版を選ぶ。
今の固定：SGLang 0.5.21、TensorRT-LLM 1.2.1、ModelOpt 0.37.0、`Qwen/Qwen3-8B-FP8`のリビジョン（`pins.sh`）。vLLMは第1段階と同じ0.31.0。

### 7. 時間・費用と、途中で止まったときの扱い

| 内容 | 時間（推定） | 根拠 |
| --- | --- | --- |
| 速さ 45セル | 約26.4時間 | 本番1回目のvLLMのスループット（1,200件÷1秒あたりの件数＋起動の約4分）から、並行数ごとに見積もった。SGLang・TensorRT-LLMもvLLMと同じ速さと仮定。FP8はbf16とAWQの間（幾何平均）と仮定。vLLMで入らなかったbf16の並行数16も、他のエンジンでは入り得るので1セル分を見込む（`make_main_cells.py`） |
| 精度 11セル | 約8.7時間 | 本番2回目・3回目の`acc-vllm-bf16`（74分）・`ni-vllm-bf16`（74分）・`ni-vllm-awq`（32分）から。FP8はその間 |
| 準備 | 約2時間 | venv 2つ・TensorRT-LLMの量子化（ModelOptで2つ作る）を足した |
| 合計 | **約39時間、約$46**（$1.167/時間） | 疎通（約4.5時間、約$5。準備と量子化を含む）を足すと約$51 |

- 自動シャットダウンは、見込みに約6時間の余りを足して2,700分（45時間）にする。本番1回目（1,080分）と同じく、測定の側に6時間で切る理由は無い（ADR-0007）。
- **途中で止まったとき**（インスタンスの停止、自動シャットダウン、回収できない失敗）：
  - 速さのセルが全部終わる前に止まったら、速さの45セルは**全部を新しいインスタンスで測り直す**。比べる値を同じインスタンスにそろえるため（ADR-0007の原則）。
    終わっていた速さのセルの値は、インスタンスの差の参考として残し、判定には使わない。
  - 速さのセルが全部終わった後に止まったら、残った精度のセルだけを新しいインスタンスで回す。greedyの答えはインスタンスの速さに左右されにくい
    （第1段階で、インスタンスの差が出たのは速さだけ）。
  - 測り直すかは、費用（月の予算）を見て、そのとき決める。測り直さない場合は、終わったところまでを報告し、比べていない構成を書く。

## 予想される反論と答え

- **「vLLMの設定に慣れているぶん、vLLMに有利では」**：3つとも既定の設定で測り、設定を詰めない。起動のコマンドはrun manifestに残る。
- **「基準を3つのbf16の平均にすると、誰が正しいか分からないのでは」**：正解は評価データの側にあり、判定しているのは正解率の差である。基準を平均にするのは、
  特定のエンジンを判定されない基準にしないため。vLLMも他と同じく判定される。
- **「2つのエンジンが同じ誤り（例：同じ読み損ね）を持つと、平均の基準では見逃すのでは」**：2つが同じだけ低いと、それぞれの差は基準の残り1つ分の半分に薄まる。
  1つだけが低い場合よりも見つけにくくなることを、限界に書く。正しい1つは片側の判定なので、他の2つより高くても通る。
- **「判定の向きは劣っていないかだけで、精度の高いエンジンが有利にならないのでは」**：足切りは「劣っていないか」だけを見て、精度の高さでは順位を付けない。
  選び方は足切りの後の台数で決める（ADR-0008の3）。
- **「なぜ信頼度を第1段階（99.5%）から変えるのか」**：第1段階は範囲の規則と組み合わせて99.5%にした。この段階では範囲の規則を置けない（検討した案）ので、
  範囲の規則なしで誤りの率を2.5%以下に保てる信頼度を、シミュレーションで結果より前に選んだ。
- **「ρ ≤ 0.3は確かめないのか」**：ρ（同じケースで入れ替わりが重なる度合い）が大きいと、誤りの率は2.5%を超え得る。第1段階の近い組の見積もりは0.13〜0.16だった（ADR-0008）。
  確かめて外したくなる規則は上の検討した案と同じ問題を生むので、前提として置き、回した後に報告して限界に書く。
- **「TensorRT-LLMだけ量子化のチェックポイントが違う」**：TensorRT-LLM 1.2.1はQwenのAWQもブロック単位のFP8も読めないので、NVIDIAの公式の道具で同じbf16から作った。
  方式の違いは「そのエンジンで公式に動く量子化」の違いとして結果に含まれ、精度は他と同じ基準で判定する。方式がそろっていないことは限界に書く。
- **「SGLangの強みのradix cacheが効かないワークロードを選んでいる」**：ワークロードは第1段階で先に決めたもので、prefix cacheが効かないこと（実測2〜9%）は限界に書いてある。
  ツール一式を固定してキャッシュが効く構成は、このプロジェクトでは測らない（検討した案）。
- **「TensorRT-LLMは本来エンジンをビルドして使うもの」**：`trtllm-serve`のPyTorchの経路（1.xの既定）で測る。ビルドの経路の方が速い可能性は残り、限界に書く。
- **「TensorRT-LLMは入れないリクエストを黙って待たせるので、並行数が名目だけでは」**：回した後に、反復ごとの統計で同時に走っていたリクエスト数を確かめる（2）。
  並行数に届いていなかったら、そのセルの数値を判定に使わない（ADR-0005の回した後の確かめと同じ扱い）。
- **「並行数の多いときのためのエンジンなのに、並行数1も測るのか」**：最大の並行数は「並行数1から続けて満たした最大の値」と決めてあり（ADR-0008の追記）、
  1を測らないと規則が第1段階と変わる。台数の表で「1台で1人もさばけない構成」を見分けるのにも、図の起点（1人で使うときの遅さ）にも要る。費用は約6時間（推定）。
- **「MLPerfの基準を使うなら、送り方もMLPerfのServer（ランダムな到着）にすべきでは」**：基準だけを借り、送り方は並行数を固定している。違いと読み方はADR-0003の追記2026-10-27。
- **「結果を見て規則を変えるのでは」**：速さの判定と選び方は第1段階の規則をそのまま使う。新しく決めるのは、候補の規則・量子化の方式・セルの範囲・
  精度の足切り（基準・信頼度・読み方）・途中で止まったときの扱いで、どれも結果より前に決める。第1段階の判定は書き換えない。

## Consequences

- 得るもの：「連続バッチングのエンジンと量子化の方式の中でどれを選ぶか」に、結果より前に決めた規則で答えられる。精度の基準も含めて同じインスタンスで取り直すので、
  インスタンスの差が混ざらない。どのエンジンも判定される基準になり、特定のエンジンが判定を免れない。新しいエンジンの精度が低い場合に、速さだけで選ばれることを防げる。
- 失うもの：約$51（疎通を含む）と1日を超えるGPU時間。第1段階の結論（vLLM AWQ）が覆る可能性がある。1回のapplyが長いので、途中で止まると測り直しが大きい。
  精度の足切りの規則が第1段階と違うので、第1段階と第2段階の判定を並べるときは、規則の違いを添える。
- 残る穴：GPUはL4 1種類、モデルはQwen3-8Bだけ。ツール定義がリクエストごとに変わる構成だけを測り、プレフィックスキャッシュが効く構成は測らない。
  送り方は並行数を固定する方式だけ。TensorRT-LLMはビルドの経路を測らず、量子化の方式も他と違う。第3パスはvLLM・llama.cppだけ。
  精度の足切りはρ ≤ 0.3を前提にし、2つのエンジンが同じ誤りを持つと見つけにくい。疎通で除外した構成があれば、その構成は比べていない。
