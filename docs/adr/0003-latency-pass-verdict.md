# ADR-0003: latencyパスは「MLPerfの8B向けレイテンシ基準を満たすか」の3値判定にする

- Status: Accepted
- Date: 2026-10-14

## Context

latencyパス（TTFT・TPOT・全体レイテンシ）の実装に入る前に、次の4点を決める必要があった。何を比べて何を主張するか、
1セルの件数、ウォームアップ、並行数の水準である。最初の案（ウォームアップ10件・1セル200件・並行数1/2/4/8）を見直したところ、
どの数字にも根拠が無いことがわかった。

- **200件**：p99について、分布の形によらない上側の限界すら出せない件数だった（0.99^n ≤ 0.05 を満たすには n ≥ 299）。
- **ウォームアップ10件**：出典は無い。`vllm bench serve`（`--num-warmups`）も NVIDIA Perf Analyzer も、ウォームアップの既定値は0件である。
  Perf Analyzer は件数ではなく、計測が安定したかどうかで判断する。
- **件数をセルごとの精度で決める案**（p99のCI半幅をp99の10%以内にする）：1つのセルの区間をどこまで狭めるかを決める話で、
  主張したい「エンジン間の比較」の精度とは別物だった。個別の区間を狭めて重なりを見るのは、vlm-vs-yoloで批判したのと同じ誤りにあたる。
- **エンジン間で最小限検出したい差を20%にする案**：Seow『Designing and Engineering Time』(2008)の「20%ルール」を根拠にしようとした。
  しかし原著（pp.71–73）を確認できず、見つかったのは読者の書評と性能UXの解説記事という二次情報だけだった。一次研究の時間弁別のWeber比は、
  条件によって約10%から30%超まで大きく変わる。引用の根拠として弱いため採用しない。
- **並行数の上限を8にした根拠**（2026-09-10、[[docs/engine-performance-plan|計画書]]）：「llama.cppは`--parallel 16`での`n_ctx`分割に耐えられない」という理由だった。
  これは検証していない推定で、同じ計画書の「並行数10前後は現実的」という記述とも食い違っていた。stage 10は1リクエストあたり約306MiBで、
  16並行なら約4.9GiB。bf16の重みを載せたあとの余白4〜5GiBに入るかどうかはぎりぎりで、「耐えられない」と言い切れる計算ではない。
  さらに今のllama.cppには統合KVキャッシュ（`--kv-unified`）がある。スロット数を自動にした場合は既定で有効になり、
  固定でN等分という前提自体が古い可能性がある（Debianのllama-server manページ。本体のソースは確認していない）。

[Source: User, latencyパスの設計の見直し, 2026-10-14]

## Decision

### 1. 主張の形：基準を満たすかの3値判定と、満たせる最大の並行数

エンジンを選ぶときに問われるのは「AはBより何割速いか」ではなく、「この並行数で、本番のレイテンシ基準を満たせるのはどのエンジンか」である。
そこで、エンジン×並行数のセルごとに、MLPerf Inference の Llama 3.1 8B 向け基準（このプロジェクトと同じ8Bクラス）を満たすかを判定する。

| 区分 | TTFT | TPOT | 判定に使う層 |
| --- | --- | --- | --- |
| 会話用（Conversational） | ≤ 2,000ms | ≤ 100ms | レイヤー1（bf16）・レイヤー2（AWQ） |
| 対話用（Interactive） | ≤ 500ms | ≤ 30ms | レイヤー2（AWQ）。レイヤー1では物理的に届かない（下記） |

- **TTFTとTPOTの両方を主な指標にする。** ツール呼び出しはJSONが最後まで生成されてから実行されるので、所要時間はおよそ
  TTFT + TPOT × 出力トークン数になる。出力は数十トークンあるので、TPOTの方が所要時間の大部分を占める。
- **1件ごとに判定する。** 1件ごとに「TTFTとTPOTの両方が基準以下か」を見て、どちらかを超えた件を「超過」と数える
  （DistServe, OSDI'24 の goodput と同じ数え方）。判定は「超過率が1%以下か」、つまりp99の水準で行う。
  MLPerfのServerシナリオの裾のレイテンシの基準（99%）に合わせたものである。ただし、LLMのTTFT/TPOTを99%で判定すると
  ルール文書に明記した箇所は見つからず、第三者の解説にもとづく読み方である。
- **3値判定**：超過の件数kと件数nから、二項分布のClopper-Pearson片側95%限界を出して判定する。分布の形は仮定しない。
  - 上限 ≤ 1% → **満たす**
  - 下限 > 1% → **満たさない**
  - それ以外 → **判定不能**
- **まとめ**：エンジンごとに「満たす」と判定された最大の並行数を出す（goodputの考え方）。エンジン間で逆転する点は、この最大並行数の違いとして示す。
- **エンジン間の比**（p50・p99の比）は、ブートストラップCIつきで記述的に報告するだけにする。最小限検出したい差は決めない。
  上記のとおり、根拠として引用できる値が無いためである。

### 2. 並行数の水準

- **全エンジン共通は 1 / 2 / 4 / 8（倍々の刻みのまま）。** 並行数1は、競合が無い状態の基準点であり、`transformers_hf`と比べられる唯一の点でもあるので外せない
  （`transformers_hf`は並行数1のみ。計画書の論点2どおり）。並行数2も残す。一度は削る案にしたが、同日に戻した。
  理由は次のとおり。1→4に飛ばすと、低い並行数の側だけ刻みが4倍に粗くなり、限界の位置を言える細かさがそろわない。
  llama.cpp（1件ずつの処理に強い）とvLLM（まとめて処理するのに強い）が逆転する点は低い並行数にありうるので、まさにその付近が粗くなる。
  そして、1セル増えても費用は数十円程度である。[Source: User, 並行数2の扱い, 2026-10-14]
- **8を超えて、各エンジンで倍々に16、32と追加する。** 「満たさない」と判定されるか、起動できない・ガードで止まる（「対応していない」と記録）
  ところまで続ける。上限は事前に32と決める。判定の形を変えたので、エンジン間で水準をそろえる必要は無くなった。
  あるエンジンがある並行数で動かないこと自体が、そのエンジンの構成上の限界を示す結果になる。
- llama.cppは疎通確認のときに `--parallel 16 --kv-unified` で起動できるか、メモリが足りるかを実測する。
  vLLMは既存の`Maximum concurrency`ガードを、latencyパスでもそのまま使う。

### 3. 件数とウォームアップ

- **1セルの件数nは、本番の前に固定する。下限は299件。** 上限は、パイロットで1件あたりの所要時間を実測し、
  6時間の自動シャットダウンの中に収まる範囲で決める。費用は1件あたり約$0.001（並行数1、L4の性能値からの概算）なので、
  件数を決めるうえで効くのは金額ではなく時間の方である。
- **「判定不能」が出ても、件数を足さない。** 結果を見てから件数を足すと、判定が都合のよい方に偏るためである。
  比較の分解能は並行数の倍々の刻みで決まり、各セルを必要以上に精密に判定しても結論は変わらない。
  2つのエンジンの限界が同じ刻みに入った場合は、「この刻みでは区別できない」と報告する。
- **ウォームアップは件数で決めず、安定したかで判定する。** NVIDIA Perf Analyzer の既定値を規則として借りる。
  5秒ごとの計測窓のうち、直近3つの窓でスループットとレイテンシのmax/minがそれぞれ10%以内に収まった時点から計測を始める。

### 4. リクエストの中身

- 14ケースのクエリを順番に繰り返し送る。ツール定義の並び順は固定する（本番に近い形：ツール定義は固定でクエリが毎回変わる）。
- **クエリの末尾に、リクエストごとに一意の識別子を付ける。** 同じプロンプトを繰り返すと、2周目以降はプロンプト全体がprefix cacheに当たり、
  TTFTが実際より極端に短く出てしまうためである。識別子を付けると、ツール定義の部分はキャッシュに当たり、クエリの部分は毎回新しくなる。
- TPOT = （全体の時間 − TTFT）÷（出力トークン数 − 1）。MLPerf・LLMPerf と同じく、TTFTを含めない。

## 検討した案

| 案 | 採否 | 理由 |
| --- | --- | --- |
| ウォームアップ10件・1セル200件 | 却下 | どの数字にも根拠が無い。200件ではp99の限界も出せない |
| 1つのセルのp99のCI半幅を10%以内にする | 却下 | 比較の精度ではなく、1つのセルの精度を決めている |
| エンジン間で最小限検出したい差を20%（Seow）にする | 却下 | 原著を確認できず、二次情報しか無い |
| エンジン間で最小限検出したい差を10%（時間弁別のWeber比）にする | 却下 | 一次研究の値が条件で大きく変わる。注意して聞き比べたときの閾値であり、実際に使っていて気づくかどうかとは別物 |
| 知覚から離れて、GPU台数の削減で決める | 却下 | 閾値を自分で決めることになり、外部の根拠が無い |
| **MLPerfの8B向け基準を満たすかの3値判定（採用）** | 採用 | 同じモデル規模に向けて公表された一次情報がある。件数がレイテンシのばらつきに依存しない。エンジン選定の意思決定にそのまま使える |

## Consequences

- **L4の帯域による下限（推定）**：bf16の8Bは、1トークン生成するたびに約16GBの重みを読み出す。L4のメモリ帯域は約300GB/s（仕様値）なので、
  TPOTの下限は約53msになる。対話用の基準（TPOT 30ms）は、どのエンジンを使っても並行数1でも届かない。
  そのため、レイヤー1は会話用の基準で判定し、対話用の基準はレイヤー2（AWQ 4bit、重み約4GB）で判定する。
  ここが「量子化すると対話用の基準に届くか」を示す場になる。下限の約53msは推定値なので、疎通確認のときに並行数1のTPOTを実測して確かめる。
- **言える結論の範囲**：「L4（24GB級の推論GPU）でbf16の8Bを動かしたとき、各エンジンはどの並行数まで会話用の基準を満たせるか」に限られる。
  全エンジンが同じ制約を受けるので比較は公平だが、ほかのGPUにそのまま一般化はできない。
- **ワークロードが違う**：MLPerfは要約タスク（入力は平均778トークン、出力は平均73トークン）である。このハーネスは、ツール定義込みで約2,200トークンの入力に
  短いツール呼び出しを返す。基準は同じモデル規模に向けた参照線として使う。
- **判定不能の幅**：MLPerfは1回あたり600秒以上計測し、早めに打ち切る場合は補正を課す。こちらは件数が少ないので、
  判定不能の幅が広めに残る（n=299なら、超過0件で「満たす」、1〜6件で「判定不能」、7件以上で「満たさない」）。
- 2026-09-10に決めた「並行数の上限は8」と、その根拠の「llama.cppは`--parallel 16`に耐えられない」はこのADRで置き換える（1/2/4/8の刻み自体は残す）。
  計画書の該当箇所には、未検証の推定だったという訂正を書く。
- 費用の数字（1件あたり約$0.001、1セル300件で全体約$2）と時間の見積もりは、L4の性能値からの概算である。パイロットの実測で置き換える。

## 追記（2026-10-15）：実装で決めたこと

latencyパスを実装する中で、次の6点を決めた（`eval_bench/latency.py`、`scripts/run_cell.py --pass-type latency`）。
[Source: User, latencyパスの実装, 2026-10-15]

### A. prefix cacheは有効のまま測り、セルの境目でリセットする

- **セルの中では自然にキャッシュに当てる。** ツール定義はキャッシュに当たり、クエリの部分は一意の識別子があるので毎回新しく計算される（4節）。
- **セルの初めに、キャッシュを空にする。** 前のセルのキャッシュが残ると、後に回したセルほど有利になり、結果が実行順で変わるためである。
  - vLLMは `POST /reset_prefix_cache` を呼ぶ。このエンドポイントは `VLLM_SERVER_DEV_MODE=1` で起動したときだけ存在し、`{"success": bool}` を返す。
    ブロックが使われている間は `false` になりうるので、3回まで再試行する（vLLMのソース `vllm/entrypoints/serve/dev/cache/api_router.py` で確認）。
  - llama.cppには、ホストRAM側のキャッシュ（`--cache-ram`）まで含めて全部消すAPIが無いので、セルごとにサーバを再起動する。
- **当たったトークン数を1件ごとに生出力のJSONLに記録する**（vLLM：`usage.prompt_tokens_details.cached_tokens`。`--enable-prompt-tokens-details` が必要。
  llama.cpp：`timings.cache_n`）。セルの最初に同時に送った件（並行数の分）のうち、少なくとも1件が0でなければ、リセットできていないとみなしてセルを打ち切る。
  マニフェストには、当たったトークンの割合を記録する。

**検討した案**

| 案 | 採否 | 理由 |
| --- | --- | --- |
| キャッシュを無効にして測る | 却下 | ツール定義を毎回計算し直す本番は無く、誰も運用しない条件でエンジンを順位付けすることになる。エンジンの差がキャッシュの扱いに出る場合、その差も消してしまう |
| **有効のまま、セルの境目でリセットする（採用）** | 採用 | vLLM `bench sweep serve`（各回の間に `/reset_*_cache` を全部呼ぶ）・SGLang `bench_serving --flush-cache` と同じやり方 |

**MLPerfとの違い（意図して変えている点）**：MLPerfの現行ルールは、クエリをまたいだキャッシュを禁止している
（inference_rules.adoc 5.1節「Caching of any other queries, query parameters, or intermediate results is prohibited」、
LLMのFAQ「KVキャッシュはクエリをまたがない範囲で許可」）。mlcommons/inference PR #2445（2026-01-14マージ）は、
これを「クエリをまたいだprefix cacheは許可されない」と明文化し、vLLMに `--no-enable-prefix-caching` を付けるよう求めている。
ただし運用は一貫しておらず、prefix cacheの扱いを問うIssue（inference_policies #300、2024-10）は公開の回答無しで閉じられ、
MLCommons自身のDeepSeek-R1・E2E-RAGの参照実装はprefix cacheを有効にしている。
禁止の理由は、2019年の論文（IV-A節）によれば「評価を簡単にするため」と、データセットが小さく丸ごと覚えられてしまうことである。
同じ箇所で「実際の推論システムはクエリをキャッシュする」とも書いている。丸ごと覚えることへの対策は、一意の識別子で済ませている。

**結果の読み方への影響**：1節のレイテンシ基準はMLPerfから借りたもので、MLPerfはキャッシュ無しの条件で計測している。
キャッシュを有効にするとprefillが軽くなるので、MLPerfより基準を満たしやすい条件で判定していることになる。
入力の長さやタスクの違い（Consequences）と同じく、基準は「同じモデル規模に向けた参照線」として使う。

**出典の確かさ**：標準化団体（MLCommons）の一次情報はMLPerfのルール文書とPRで、prefix cacheを禁止していることまでは確認できた。
vLLM・SGLangはツールの動作の記述で、「こう測るべき」という規範ではない。InferenceX（SemiAnalysis、民間の調査会社）は、
ランダムなデータセットではprefix cacheを無効にし、エージェント向けのAgentXでは有効にしてヒット率を報告している、
と用語集に書いている。ただしこれは要約ツール越しに読んだだけで、実験の設定ファイルは確認していない。
エージェント向けのワークロードでprefix cacheをどう扱うかを定めた、専門機関の基準は見つからなかった。
有効にしたまま測る主な根拠は、本番と同じ条件で測るという理由づけであり、出典は同じ判断をしている例として補強するにとどまる。
[Source: User, prefix cacheの扱いの確認, 2026-10-15]

### B. ウォームアップの窓は「ケースセット1周分の件数」

3節の「5秒ごとの計測窓」は、並行数1では成り立たない。1件に約2.5秒かかる（推定：出力約40トークン × TPOT約53ms ＋ prefill）ので、
5秒の窓には2件か3件しか入らず、エンジンの状態が同じでも、窓の境目にかかるかどうかだけでスループットが33〜50%動く。
Perf Analyzerは10窓（`--max-trials`）で安定しなければ打ち切るので、並行数1のセルは必ず失敗する。

そこで、Perf Analyzerのもう1つのモード（`count_windows`：時間ではなく完了件数で窓を区切る）の形にする。

- **1窓 = ケースセット1周分の件数**（今は14件）。並行数1では、どの窓にも同じクエリが1回ずつ入るので、窓どうしの差はエンジンの状態だけを反映する（導出）。
  Perf Analyzerの`count_windows`の既定値（`--measurement-request-count=50`）は使わない。並行数1でウォームアップが最短でも約6分かかり、窓ごとのクエリの構成もそろわないためである。
- 判定の規則はPerf Analyzerの既定のまま：直近3窓で、スループットと平均レイテンシのmax/minがそれぞれ10%以内（`--stability-percentage`、
  レイテンシは`--percentile`未指定時の既定どおり平均）。10窓で安定しなければセルを打ち切る（`--max-trials`）。
- **安定した時点の後に送ったリクエストから、n件を計測する。** 計測した件がすべて終わるまで同じ並行数で送り続け、
  余分に送った件は「cooldown」として記録だけして数えない。終わり際に並行数が下がった状態の件を計測に混ぜないためである。
- **未確認の点**：並行数が大きいと、窓の長さに「どの件がたまたま先に終わったか」による揺れが、おおよそ窓の件数分の1（14件で約7%）入る（推定）。
  10%の基準に近いので、並行数16・32のセルが安定判定を通るかをパイロットで確かめる。通らなければ、窓を「ケースセット何周分か」に広げる（その時点で決める）。

### C. エラーの扱いは種類で分ける

vLLMもllama.cppも、混んでいるときにリクエストを断らず列に並ばせる。そのため、タイムアウト以外のエラーは「混んでいるから時々起きる」ものではなく、
そのセルの設定では動かないことを示す。

- **タイムアウト**（既定120秒）**→ 超過として数える。** 基準のTTFT 2秒を確実に超えているので、選ぶ余地が無い。パーセンタイルには含めず、件数を別に記録する。
- **HTTPエラー・接続エラー・ストリーム中のエラー・thinkingの出力 → セルを打ち切る。** マニフェストではなく `<run_id>.aborted.json`
  （`"outcome": "unsupported"`）を書き、2節の「対応していない」として扱う。設定の問題を、レイテンシの裾の問題と混ぜないためである。

### D. TTFTと全体の時間の定義

- **TTFT**：`choices`を含む最初のストリームのチャンクが届いた時刻（vLLM `bench serve` の `async_request_openai_chat_completions` と同じ。ソースで確認）。
  ツール呼び出しのパーサは、関数名が読めるまで差分を送らないことがあるので、本文やツール呼び出しの断片を含む最初のチャンクの時刻も別に記録し、実機で両者を比べる。
- **全体の時間**：`choices`を含む最後のチャンクまで（同じくvLLM `bench serve` に合わせる。末尾のusageだけのチャンクはトークンを運ばない）。
- **transformers_hf**：サーバを持たないので、`generate()`が1トークンごとに呼ぶ停止条件のフックで時刻を取る（CUDAを同期してから記録する）。
  TTFTは、チャットテンプレートを組み立てる前から測る（サーバのTTFTにはテンプレートの処理とトークン化が含まれるため）。

### E. ツール定義はケースごとに固定する

4節の「ツール定義の並び順は固定する」は、ケースごとのツール集合を、`build_tool_set`のseed=0の並びのまま毎回使う、という意味で実装した。
ステージ10ではケースごとに正解ツールと紛らわしいツールが違い、1つの共通の10個に全ケースの正解を収められないためである。
そのため、キャッシュに載るツール定義はケースの数だけ（今は14通り）ある。並行数が大きいときにキャッシュから追い出されるかは、
当たったトークンの割合として結果に出る。

### F. ケースの数（14件）は検討していない

4節の「14ケース」は、`data/`に最初のコミット（2026-08-16）からある件数をそのまま使ったもので、件数の妥当性は検討していなかった
（Article1用に、手作り5件・意図的に難しくした5件・有価証券報告書に接地した4件の3通りの作り方を見せるためのセット）。

- **判定の精度には効かない。** Clopper-Pearsonの計算に入るのはリクエストの件数nと超過の件数だけで、ケースの数は「どんな混ざり方で測ったか」を決めるだけである。
  ケースを1周ずつ均等に送るので、ケースによって超過しやすさが違っても、超過件数のばらつきはランダムに選ぶ場合より小さく、判定は安全側になる。
- **条件1：本番の前に固定する。** 結果を見てからケースを入れ替えると、判定が偏る（3節の「件数を足さない」と同じ理由）。
- **条件2：言える範囲は「そのケースセットを繰り返し送ったとき」に限られる。** 何件あれば本番のワークロードを代表できるかを決める統計の式は無い。記事に限界として書く。
- **latencyパスは、第3パスと同じケースセットを使う。** ADR-0002で第3パスのケース数はパイロットで決めることになっており、ケースを増やすならlatencyパスも同じセットにそろえる。
  実装は件数に依存しない（窓もケースセット1周分として決まる）。

### G. 「対応していない」の判定は、ADR-0005の`capacity_check`で行う

2節の「vLLMは既存の`Maximum concurrency`ガードを、latencyパスでもそのまま使う」は、[[docs/adr/0005-capacity-check|ADR-0005]]で置き換えた。
「対応」の定義は**保証型**で、全リクエストが同時に最大の長さ（プロンプトの最大＋`max_tokens`）まで伸びても入りきることを指す。全エンジンに同じ式で当てる。

第三者に「この水準の組み方でよいか」と問われたときの答えとして、次の3点を明記する。

- **保証型は、一般的なベンチマークより厳しいが、このワークロードでは判定がほとんど変わらない。** `vllm bench serve`などは、メモリが足りなければ待たせたまま測り、
  その待ちもレイテンシに含める。こちらは事前の判定で外す。ただし、1リクエストの最大3,078トークンのうち2,566がプロンプトなので、最悪の見積もりは
  実際の長さ（約2,600）より約18%多いだけである（導出）。実際の長さで数えても、vLLM bf16の並行数16（約11本まで）とllama.cppの並行数32（約83,000トークンが必要）は
  載らず、判定は変わらない。違いが出うるのは、余りの少ないvLLM AWQの並行数32だけである。
- **届く最大の並行数を、数字でも併記する。** 倍々の刻みだけでは「8と16の間」としか言えないので、事前の判定から出る「保証して載せられる最大の並行数」
  （vLLM bf16は9本、AWQは32本）を添える。llama.cppは上限を探さないので、「16は対応、32は対応していない」と、空きメモリからの見積もりを推定として添える。
- **上限32は、物理的な限界と一致する。** 保証型の基準のもとで、vLLM AWQのKVキャッシュ（99,552トークン）がちょうど並行数32で尽きる。

エンジンによって届く並行数がそろわない（見込みでは、vLLM bf16は8まで、llama.cpp bf16は16まで、vLLM AWQは32まで）のは、2節のとおり意図した結果である。

### H. パイロットのセル一覧

パイロットで決めるのは、本番の件数（latencyパスのn）、第3パスのケース数（ADR-0002）、高い並行数での安定判定（追記B）の3つである。
中間の並行数（2/4/8）は本番で回すので、パイロットには入れない。

| セル | 扱い | 理由 |
| --- | --- | --- |
| 第3パス：vLLM AWQの並行数1・16 | 入れる | ADR-0002のケース数を決める |
| latency：3エンジンの並行数1 | 入れる | 1件あたりの所要時間から、本番のnを決める |
| latency：vLLM AWQの並行数16・32 | 入れる | vLLMの高い並行数での安定判定を試す |
| latency：llama.cpp bf16の並行数16 | 入れる | llama.cppの高い並行数での安定判定を試す |
| latency：vLLM bf16の並行数16・32 | 入れない | 事前の判定で「対応していない」（保証して載るのは9本）。本番では事前の判定が記録する |
| latency：llama.cpp bf16の並行数32 | 入れない | 98,496トークンが要り、空きメモリからの見積もり（約58,000）に入らない（推定）。本番では起動を試して記録する |

高い並行数のセルは、vLLMがAWQ、llama.cppがbf16で層が混ざる。パイロットは件数と安定判定の調整だけに使い、エンジン間の比較には使わない。
所要時間は、疎通の並行数1の1件あたりの時間（vLLM AWQ約1.7秒、vLLM bf16約3.3秒、llama.cpp約3.6秒）から約4.5時間と見込む（推定）。
6時間に収まらなかったときに備えて、一覧は大事な順（第3パス → 並行数1 → 高い並行数）に並べる。

### I. bf16の層の低い並行数は、「並行数が高いならvLLM」という前提の確かめにも使う

ADR-0002の追記（2026-10-19）で、第3パスをvLLM AWQに限った。その前提（業務の並行稼働はvLLMが中心）を、出どころだけに頼らないために、
2節の全エンジン共通の1/2/4/8で、vLLMとllama.cppの差が出始めるかを見る。2節の水準は変えない。
