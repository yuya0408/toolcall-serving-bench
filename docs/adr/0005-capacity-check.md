# ADR-0005: 並行数のセルが成り立つかを、全エンジン共通の容量の判定（`capacity_check`）で確かめる

- Status: Accepted（2026-10-27。本番3回のapplyで、追記を含めたこの決定どおりに動かした）
- Date: 2026-10-19

## 結論（Summary）

- 並行数のセルは、要件（同時にc本、1本あたり入力の最大＋`max_tokens` 512）を全エンジンで同じにして比べる。
- 回す前に「c × 1本の最大 ≤ KVキャッシュの容量」を計算で確かめ、入らなければ「対応していない」と記録する。設定を上げて載せることはしない。
- 回した後に、追い出し・打ち切り・入力の長さを確かめ、容量不足が起きていないことを確かめる。
- vLLMはメモリの割合を既定のまま。llama.cppは`--ctx-size`を要件から決め、KVはスロットごとに分ける（追記2026-10-21・23）。

## 背景と問い（Context and Problem Statement）

並行数が2以上のセル（latencyパスと第3パス）では、そのエンジンのKVキャッシュに、同時に送るリクエストがすべて入りきるかを確かめる必要がある。
入りきらないと、エンジンは処理中のリクエストを中断して計算し直したり（vLLMのpreemption）、受付で待たせたりする。そうなると、測っているものが
「その並行数でのエンジンの性能」ではなく「容量不足のときの振る舞い」に変わる。

これまでの仕組み（`eval_bench/runner.py`の`parse_vllm_diagnostics`、`vllm_diagnostics`）は、1回目のapply（疎通、2026-10-18）で次の理由で働かなかった
（詳細は`docs/gpu-smoke-2026-10-18.md`のD1・D2・D7）。

- **読み取りの書式**：vLLMの起動ログから`# GPU blocks: N`と`Maximum concurrency`を読んでいたが、vLLM 0.31.0のログにはブロック数の行が無く、数字にカンマが入る。
  起動ログは人が読むための出力で、書式は版で予告なく変わる。
- **判定の基準**：`Maximum concurrency`は「すべてのリクエストが`max_model_len`（8,192）を使い切る」前提の値で、実際のリクエスト（最大約3,100トークン）よりずっと長い。
  AWQの並行数16は、実際には余裕で入るのに捨てられた。
- **vLLM専用**：llama.cppには同じ確かめが無かった。疎通では、llama.cppの並行数16は実際の出力が短かった（最大51トークン）ので回っただけで、
  最大の長さで数えると`--ctx-size 40960`には入らない。
- **エンジン間でメモリの決め方がそろっていない**：vLLMは既定でGPUの92%を使い、作業領域を先に取った残りをすべてKVにする。llama.cppは`--ctx-size`で指定した分だけKVを取る。
  疎通の「llama.cppは並行数16が載り、vLLMは載らない」は、エンジンの実力より設定の差から来ていた可能性が高い。
- **容量が起動ごとに変わる**：vLLMの起動8回のうち、新しいインスタンスで最初に起動した2回だけ、KVがちょうど1.00GiB少なかった
  （bf16は30,240トークンが22,992に、AWQは99,552トークンが92,240に。設定はすべて既定の0.92）。原因は分かっていない。

## 検討した案（Considered Options）

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 起動ログの読み取りを、0.31.0の書式に合わせて直す | 却下 | 書式は版で予告なく変わる。機械が読む値は、機械向けの口（`/metrics`）から取る |
| `Maximum concurrency`（`max_model_len`を使い切る前提）≥ c で判定する | 却下 | 実際のリクエストより2倍以上長い前提で、載る構成を捨てる |
| 待ち時間でセルを捨てる | 却下 | ステップの上限による待ちとKV不足を区別できない（3節） |
| KVキャッシュの総量そのものを全エンジンで揃える | 却下 | エンジンの効率だけを切り出すときの方法。運用で揃えるのは「1リクエストに保証する長さ」 |
| 余白をllama.cppの`--fit-target`の既定値1,024MiBにそろえる | 却下 | READMEに既定値はあるが、理由の説明が無い。issue #18390で挙がる用途は画面表示を兼ねるGPUなどデスクトップ向けで、画面の無いサーバーではOSはGPUのメモリを使わない |
| vLLMの`gpu_memory_utilization`を0.98から下げて、回せる最大の値を実測で探す | 却下 | 上げても判定が変わるセルが無い |
| llama.cppの`--ctx-size`の上限を、起動の試し直しで探す | 却下 | 判定に効かず、併記する数字の精度が上がるだけ（約10〜15分のGPUの時間） |
| 最悪の長さではなく、実際の長さ（約2,600トークン）で判定する | 却下 | 保証にならない。このワークロードではプロンプトが大半を占め、最悪の見積もりは実際の長さより約18%多いだけで、判定はほとんど変わらない（ADR-0003の追記G） |

## 決定（Decision Outcome）

### 1. 要件を全エンジンで同じにし、各エンジンは要件ぶんだけメモリを載せる

一般的な比べ方は2つある。(1) ハードウェアを固定し、各エンジンが設定を最善にする（MLPerf InferenceのClosed部門：モデル・精度・遅延の基準は固定し、
システムの調整は提出者に任せる）。(2) 要件（同時にc本、1リクエスト最大Lトークン、遅延の基準）を固定し、各エンジンをその要件に合わせて設定する（容量計画）。
このプロジェクトの問い（ADR-0003：この並行数で、本番のレイテンシ基準を満たせるのはどのエンジンか）は(2)の形なので、(2)を採る。

- **要件**：並行数cと、1リクエストの最大 ＝ そのセルが送るプロンプトの最大長 ＋ `max_tokens`（512で固定）。全エンジンで同じ。
- **vLLM**：`--gpu-memory-utilization`は既定の0.92のまま変えない。普段の起動で、計画した並行数（bf16は8まで、AWQは32まで）がすべて載り、
  上げても判定が変わるセルが無い（bf16の16は0.97にしても約12本で届かず、AWQの32は既定で載る。導出）。エンジンの既定値を使えば、余白の量という根拠の無い数字を持ち込まない。
- **llama.cpp**：セルごとに`--ctx-size` ＝ c × 1リクエストの最大（を切り上げた値）にし、`--kv-unified`で全スロットが共有する。`--fit off`を明示する
  （既定のonでは、設定していない引数をメモリに収まるよう黙って縮めうるため。使うコミットに`--fit`が無ければ指定しない）。
  起動したときにllama.cppが報告する実際の`n_ctx`を容量として記録する。（2026-10-21訂正：`n_ctx`は1スロットの上限で、総容量ではなかった。総容量は`--ctx-size`から取る。末尾の追記を参照）
  （2026-10-23訂正：`--kv-unified`はやめ、スロットごとに分ける既定の`--no-kv-unified`にした。分割で起動できなければ1回だけ統合に戻す。末尾の追記2026-10-23を参照）
- **上限は探さない。** 探しても判定は変わらず、併記する数字の精度が上がるだけである。

### 2. 事前の判定：GPUの時間を使う前に、入りきるかを計算で確かめる

判定は「1リクエストの最大を割り当ての単位で切り上げ、c倍したもの ≤ KVキャッシュの容量」。この「対応」の定義は**保証型**である。
全リクエストが同時に最大の長さまで伸びても、KVが理由で受付が止まらないことを保証する。

- **プロンプトの最大長**は、手元で数える（GPUは要らない）。`run_cell`と同じ関数（`build_tool_set`・`trial_order`・`to_openai_tools_subset`）で
  そのセルが送る全リクエストを組み立て、Qwen3-8Bのトークナイザ（固定したリビジョン）の`apply_chat_template(..., add_generation_prompt=True, enable_thinking=False)`で数える。
  latencyパスはクエリの末尾の識別子（約22トークン）も含める。疎通の実測では、この数え方はvLLMの`prompt_tokens`と90件すべてで一致し（識別子の分で±1）、
  llama.cppは常に4トークン少なかった。数えた値に割り当ての単位1つ分（vLLMは16トークン）を足して、エンジン間のずれを吸収する。
  （2026-10-20訂正：「llama.cppは常に4トークン少ない」はエンジンの差ではなかった。識別子がランダムな16進数で、英字のまとまり方によってトークン数が変わり（末尾の識別子全体で16〜22）、vLLMのセルとllama.cppのセルで違う識別子を引いていたためである。llama.cppは同じテンプレートをHFと1トークンも違わず描画する（手元のb11716で確認）。識別子は数字8桁に変え、値によらずトークン数が一定になった。数え直した最大値は2,591のままで、判定は変わらない）余裕の1単位は、確かめていないエンジン間の差への備えとして残す。
- **容量**は、vLLMは`/metrics`の`vllm:cache_config_info`（`num_gpu_blocks` × `block_size`）から、サーバーの起動後に1回読む。llama.cppは起動時に報告された`n_ctx`。（2026-10-21訂正：llama.cppは`--ctx-size`を総容量とし、`/props`の`n_ctx`は1スロットの上限として別に確かめる。末尾の追記を参照）
- **足りないとき**：
  - vLLMは、サーバーを1回だけ起動し直して読み直す（少なく出たのは、新しいインスタンスで最初の起動だけだったため）。それでも足りなければ「対応していない」。起動し直したことも記録する。
  - llama.cppは、要件どおりの`--ctx-size`で起動できなければ（`server_not_ready`）「対応していない」。
- 「対応していない」はADR-0003のとおり結果として記録し、やり直さない。

### 3. 事後の確かめ：回した後に、容量不足が起きなかったかを確かめる

| エンジン | 確かめる値 | 出どころ |
| --- | --- | --- |
| vLLM | 中断して計算し直した回数（`vllm:num_preemptions`）のセルの前後の差が0 | `/metrics`。累積の値なので、前後の2回で取りこぼしが無い |
| llama.cpp | エラーで返ったリクエストの数と、終了理由が長さの上限だったリクエストの数が0 | 生出力。llama.cppには中断の回数にあたるメトリクスが無く、統合KVを使い切ったときの振る舞いも確かめていないため |
| 両方 | 実測したプロンプトの最大長が、事前に数えた値を超えていない | 生出力の`usage`。精度パスの生出力にも`usage`を残す |

（2026-10-23訂正：llama.cppの行の「エラーで返ったリクエストの数が0」は、事後の確かめでは数えていない。エラーは1件でも出た時点でセルを止めるので、
0であることは別の場所で保証されている。latencyパスはtimeout以外のエラーでセルを打ち切って「対応していない」と記録し（`eval_bench/latency.py`）、
精度パスは例外でセル全体が`error`で終わる。timeoutは容量不足の目印ではなく、ADR-0003の判定で「基準を超えた」1件として数える。
「長さの上限だったリクエスト」は、出力が`max_tokens`に達したものを除く。追記2026-10-23を参照）

| 事前の判定 | 事後の確かめ | 扱い |
| --- | --- | --- |
| 載らない | （回さない） | `unsupported`。結果として記録し、やり直さない |
| 載る | 問題なし | 通常の結果 |
| 載る | 問題あり | 見積もりの誤り。数字は判定に使わず、原因を調べるまで同じ構成の高い並行数は回さない。生のデータは残す |

**待ち時間は、捨てる条件に使わない。** vLLMは1ステップで処理するトークン数に上限（`max_num_batched_tokens`）があり、並行数16で約2,400トークンのプロンプトが一斉に届くと、
KVに余裕があっても後ろのリクエストは数ステップ待つ。これは並行処理のエンジンが普通に持つ挙動で、その構成の性能に含まれる。
待ちの理由別のメトリクス（`vllm:num_requests_waiting_by_reason`）も理由は`capacity`と`deferred`の2つだけで、KV不足とステップの上限を区別できない（vLLM 0.31.0のソースで確認）。
KV不足が起こす2つの現象は、受付で待たされることを事前の判定で、処理中に中断されることを事後の中断の回数で押さえる。待ち時間（`vllm:request_queue_time_seconds`の前後の差）は記録だけする。

### 4. マニフェストの`capacity_check`

vLLM専用の`vllm_diagnostics`を、全エンジン共通の`capacity_check`に置き換える。並行数が2以上のセルでは必須にする。

| 欄 | 中身 | 出どころ |
| --- | --- | --- |
| `capacity` | KVキャッシュの容量（単位・単位の大きさ・数・トークン数） | vLLMは`vllm:cache_config_info`、llama.cppは起動時の`n_ctx` |
| `required` | （1リクエストの最大 ＋ 余裕）を単位で切り上げ、c倍したもの | 事前の計算 |
| `max_prompt_tokens_planned`・`max_prompt_tokens_observed` | 事前に数えた値と、実測の最大値 | 手元のトークン化、`usage` |
| `restarts` | 容量が足りずにサーバーを起動し直した回数（vLLMのみ。0か1） | `run_cell` |
| `post_check` | vLLMは中断の回数。llama.cppはエラーの件数と打ち切りの件数（`max_tokens`まで出して止まったものは除く。追記2026-10-23） | `/metrics`の前後の差、生出力 |
| `queue_time`（vLLMのみ） | 待ち時間の合計・件数・ヒストグラムの区間ごとの件数（記録だけ） | `/metrics`の前後の差 |
| `startup_log_max_concurrency`（vLLMのみ、任意） | 起動ログの`Maximum concurrency`（照合用。読めなければ省く） | 起動ログ |

## 影響（Consequences）

- **普段の起動での容量**（導出。1リクエストの最大は、ADR-0004の追記でケースとツールの説明を直した後に`scripts/count_prompt_tokens.py`で数えた
  プロンプトの最大2,591（case_1132、カタログ2.1.1）＋ 512 ＝ 3,103トークン。vLLMは余裕16トークンを足してブロックで切り上げ、3,120）：

  | 構成 | 容量 | 保証して載る本数 | 1GiB少ない起動では |
  | --- | --- | --- | --- |
  | vLLM bf16（0.92） | 30,240トークン（実測） | 9本 | 7本 |
  | vLLM AWQ（0.92） | 99,552トークン（実測） | 31本（並行数32には288トークン足りない） | 29本 |
  | llama.cpp bf16 | `--ctx-size`しだい | 並行数16（49,648トークン）は載る見込み。空きメモリから約16〜18本（推定） | — |

  数え方は、疎通のlatencyのセル（修正前のケースとカタログ）でケースごとの最大値がvLLMの`prompt_tokens`と20件すべてで一致し、llama.cppより常に4トークン多かった。
  （2026-10-20訂正：「llama.cppは常に4トークン少ない」はエンジンの差ではなかった。識別子がランダムな16進数で、英字のまとまり方によってトークン数が変わり（末尾の識別子全体で16〜22）、vLLMのセルとllama.cppのセルで違う識別子を引いていたためである。llama.cppは同じテンプレートをHFと1トークンも違わず描画する（手元のb11716で確認）。識別子は数字8桁に変え、値によらずトークン数が一定になった。数え直した最大値は2,591のままで、判定は変わらない）
- **vLLM AWQの並行数32は「対応していない」になる。** 修正前の数え方（プロンプトの最大2,566）では余り224トークンで載っていたが、ツールの説明を直して最大が25トークン伸び、
  載らなくなった。決めたとおり、設定を上げて載せることはしない。実際の長さなら入るので、保証型を選んだことの帰結として記録する（ADR-0003の追記G）。
- **llama.cppの最大の並行数は、数字では言えない。** 上限を探さないので、「16は対応、32は対応していない」と、空きメモリからの見積もりを推定として添える。
- **llama.cppの事後の確かめは弱い。** 中断の回数にあたる値が無く、統合KVを使い切ったときの振る舞いも確かめていない。エラーと打ち切りの件数で見るが、
  黙って遅くなる形の容量不足があれば見逃す。
- **1GiB少ない起動の原因は分かっていない。** 次のapplyでも起動ごとの容量を記録し、起きるかを確かめる（手順書に書く）。
  （2026-10-22のapplyでも、新しいインスタンスの最初の起動（capacity-smokeのvLLM AWQ）だけが92,240トークンで、その後の起動はすべて99,552だった。
  92,240でも並行数16の必要量49,920には足りたので、2節の起動し直しは起きなかった）
- **ADR-0003の2節「vLLMは既存の`Maximum concurrency`ガードを、latencyパスでもそのまま使う」は、このADRで置き換える。**

### A1 追記（2026-10-21）：llama.cppの総容量は`--ctx-size`から取り、`/props`の`n_ctx`は1スロットの上限として確かめる

**起きたこと。** 2回目のapplyの`capacity-smoke.json`で、llama.cppの並行数16のセルが事前の判定で`unsupported`になった。
`--ctx-size 49664 --parallel 16 --kv-unified`で起動したが、`/props`の`n_ctx`は40,960だった。起動ログには
「the slot context (49664) exceeds the training context of the model (40960) - capping」「n_slots = 16, n_ctx_slot = 40960」とある。
llama-serverは、1スロットの文脈長をモデルの学習時の長さ（Qwen3-8Bの`n_ctx_train` 40,960）までに切り詰め、共有するKVキャッシュは`--ctx-size`のまま確保する。
`/props`の`n_ctx`は1スロットの上限で、総容量と一致するのは、総容量が学習時の長さ以内のときだけだった。
疎通（2026-10-18）は`--ctx-size 40960`で起動しており、ちょうど上限で切り詰めが起きなかったため、この違いが見えなかった。

**版の違いではない。** 2回目のapplyのllama.cpp（b11785、8baabd5）は疎通（848bbda）と違うが、手元のb11716（CPU版）とQwen3-0.6B
（`n_ctx_train`は同じ40,960）で同じ起動をすると、同じく40,960に切り詰められた。2節の「llama.cppは起動時に報告された`n_ctx`」が、
総容量が学習時の長さを超える場合を想定していなかった。容量そのものは足りていた。

**総容量を返す口が無い。** llama-serverのREADMEでは、`/props`の`n_ctx`も`/slots`の各スロットの`n_ctx`も1スロットあたりの値で、
`/metrics`にも容量の項目は無い（あるのは実際に使った最大の`n_tokens_max`）。起動ログの警告には`n_ctx_seq (49664)`と総量が出るが、
上限を超えたときにしか出ず、文言は版で変わりうる。

**決めたこと。**
- llama.cppの総容量（`capacity.tokens`）は、起動に使った`--ctx-size`とする。根拠は`--kv-unified`の仕様（全スロットで1つのKVバッファを共有する、README）。
- `/props`の`n_ctx`は`capacity.per_slot_tokens`として記録し、「1リクエストの最大＋余裕1単位 ≤ 1スロットの上限」も判定に加える。総容量と1スロットの両方が足りるときだけ`fits`。
- 事後の確かめ（3節：長さの上限で止まった応答とエラーが0）は変えない。総容量の見立てが外れていれば、ここで捕まる。
- この判定で、2回目のapplyの値は総容量49,664 ≥ 必要49,664、1スロット40,960 ≥ 3,104で`fits`になる。

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 総容量を起動ログの警告（`n_ctx_seq`）から読む | 却下 | 上限を超えたときにしか出ない。文言は版で予告なく変わる（vLLMの起動ログを却下したのと同じ理由） |
| llama.cppのコミットを疎通の版に固定して直す | この件では却下 | 疎通の版でも同じく切り詰める（手元のb11716で確認）。apply間で版を固定するかは別に扱う |
| YaRNで学習時の長さを延ばし、切り詰めを避ける | 却下 | モデルの振る舞いが変わり、vLLMと同じ条件で比べられなくなる |

**あわせて直したもの。** `scripts/gpu/check_llama_seed.py`が、プロンプトの予算を渡さずにllama.cppのサーバーのコマンドを作っており
（このADRで`--ctx-size`を予算から決めるようにした後）、2回目のapplyで落ちて`checks/llama_seed.json`が作られなかった。
並行数1のセルと同じ大きさで起動するようにした。

### A2 追記（2026-10-23）：llama.cppの事後の確かめは、max_tokensまで出して止まった応答を数えない

**起きたこと。** 2回目のapply（pilot-1）で、llama.cpp bf16の並行数16のlatencyのセルが事後の確かめに落ちた（`capacity_misestimate`）。
原因は、cooldownの1件（case_1120、ツールを呼ばずに文章で答えるケース）が`max_tokens`の512トークンを出し切って止まったことだった。
同じケースは並行数1でも毎回512で止まっている。server.logの各応答の`truncated`は933件すべて0で、文脈が尽きて止まった応答は無かった。

**原因。** OpenAI互換APIの`finish_reason`は、`max_tokens`に達したときも文脈が尽きたときも`"length"`を返す。llama-serverは内部では
文脈が尽きたときに`truncated`を立てる（`tools/server/server-context.cpp`、コミット848bbda）。独自の`/completion`とログにはこの値を出すが、
`/v1/chat/completions`の応答には載せない。3節は`"length"`をすべて容量不足の目印として数えていた。

**決めたこと。**
- `"length"`で止まった応答のうち、出力が`max_tokens`に達したもの（`usage.completion_tokens`、latencyでは`output_tokens`）は数えない。
  出力の上限は事前の判定で1リクエストぶん確保している（2節の「プロンプトの最大＋512」）ので、容量の見積もりとは関係がない。
  数えるのは、`max_tokens`に届かずに止まったもの（文脈が尽きたもの）だけにする。
- 出力の長さが読めない応答は区別できないので、これまでどおり数える。
- マニフェストの`length_finished`は意味を変えずに残し（`"length"`で止まった全件）、そのうち`max_tokens`に達したものを`output_limit_finished`として記録する。
  これを持たない前のマニフェストもスキーマを通る。
- warmup・cooldownも含めて、全区間の応答を数える（変更なし）。事後の確かめが見るのは数値ではなく見積もりの正しさで、
  文脈が尽きたのなら区間によらずスロットの文脈が足りなかったことになり、計測区間でも同じことが起こりうる。
- この判定で、pilot-1の該当セルは事後の確かめを通る（`length_finished` 1、`output_limit_finished` 1）。

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 計測区間（measured）の応答だけを数える | 却下 | 見積もりの誤りは区間を選ばない。今回の誤検知は数え方の誤りで、区間を絞っても、計測区間で同じ形の応答があれば同じく落ちる |
| server.logの`truncated = 1`も数える | 今回は見送り | エンジン内部の値なので直接的だが、ログの書式は版で変わりうる（起動ログを却下したのと同じ理由）。応答側の判定はソースの条件と一致しており、ログは食い違いが出たときの確かめに使う |
| llama.cppに、互換APIの応答にも`truncated`を載せるよう要望する | 見送り | `finish_reason`の曖昧さはOpenAIの仕様に由来する（vLLMも同じ）。応答側の回避策で足りている |

### A3 追記（2026-10-23）：llama.cppのKVキャッシュは、スロットごとに分ける（エンジンの既定）。起動できなければ1回だけ共有に戻す

**きっかけ。** pilot-1で、llama.cpp bf16の並行数16のlatencyのセルが極端に遅かった（TPOTの中央値1,384ms、並行数1は61ms。
プロンプトの処理はリクエストあたり2,091→391 tokens/s、生成は59.5→1,322 ms/トークン、server.logの各応答の記録から）。
調べる中で、1節で入れた`--kv-unified`（全スロットで1つのKVキャッシュを共有する）が、エンジンの既定から外れた設定で、入れた理由も記録されていないことが分かった。
llama-serverのヘルプでは、`--kv-unified`の既定は「スロット数を自動にした場合だけ有効」で、`--parallel`を明示するこのプロジェクトでは既定は分割である。
疎通の記録（`docs/gpu-smoke-2026-10-18.md`のD7）には「vLLMのページ方式と同じく、リクエスト間でKVを共有する方式」とあり、これが実質の理由だった。

**統合と分割の違い**（llama.cppのソース、コミット848bbda）：
- 統合では全スロットが1つのストリームを使い、attentionの対象の長さ（`n_kv`）は、ストリームで使われているいちばん後ろの位置までになる（`src/llama-kv-cache.cpp`の`get_n_kv`）。
  ほかのスロットのトークンはマスクで除かれるが、計算から外れるかはバックエンドしだいである。CPUは1つずつ読み飛ばし（`ggml-cpu/ops.cpp`）、
  CUDAには見える位置だけを集める経路がある（`ggml-cuda/fattn.cu`）が、使われる条件は込み入っていて、pilot-1で使われたかは分からない。
- 分割ではスロットごとにストリームを持ち、attentionは自分のトークンだけを対象にする。
- vLLMのページ方式が共有しているのはメモリの割り当てで、attentionは自分のリクエストのブロックしか読まない。D7の「同じ方式」は割り当ての面だけで、
  attentionの面では分割のほうがvLLMに近い。
- 手元のCPU（b11716、Qwen3-0.6B、4本同時）では、統合と分割で速さに差は出なかった（生成506と490 ms/トークン）。上のとおりCPUはマスクされた位置を読み飛ばすので、
  GPUでの差の有無はこの結果からは言えない。

**決めたこと。**
- llama.cppは`--no-kv-unified`（エンジンの既定）で起動する。理由は速さではなく、2節の方針（性能の設定はエンジンの既定を使い、要件を満たすのに必要なものだけを変える）に、
  `--kv-unified`が理由なく外れていたことである。保証型の判定（1リクエストの最大を本数ぶん確保する）では、統合の利点（スロット間で容量を融通する）は使わない。
  分割の方が遅かったとしても、分割にする。
- 分割では、llama.cppが1スロットの長さを256トークンの倍数に切り上げ、全体をその長さ×スロット数にする（`src/llama-context.cpp`、手元のb11716でも確認）。
  そこで`--ctx-size`は「1リクエストの最大＋余裕1」を256の倍数に切り上げた値×並行数とし（3,104→3,328、並行数16で53,248）、渡した値と確保される値を一致させる。
  vLLMが16トークンのブロック単位で切り上げる（3,120）のと同じく、エンジンの割り当ての単位として扱う。
- 容量は`/props`の`n_ctx`（1スロット）×`total_slots`とする。エンジンが報告する値だけで決まり、追記2026-10-21の「全体は`--ctx-size`から取る」は統合に戻したときだけ使う。
- **並行数2以上で、分割で起動できなければ、1回だけ統合（全体を1回だけ切り上げる）で起動し直す。** 切り替えは起動できたかどうかだけで決まり、遅延の結果は見ない。
  統合でも起動できなければ`server_not_ready`（対応していない）。どちらで回ったかは`capacity_check.json`と`status.jsonl`の`llama_kv`に残す。
  並行数1では2つは同じキャッシュになるので、切り替えない。
- チャンクの大きさ（llama.cppの`n_batch`、vLLMの`max_num_batched_tokens`）は既定値のままにする。値は各セルの記録（`engine-*`）に残る。

**見込み**（導出、推定）：並行数16の分割は53,248トークンで、統合の49,664より3,584トークン（KVは1トークンあたり36層×8ヘッド×128×2×2バイト＝147,456バイトで約504MiB）多い。
pilot-1の並行数16（統合）はGPUのメモリを21,832MiB使っており、分割では約22,340MiBの見込みで、L4の23,034MiBに対して約700MiBの余裕がある。
分割ではattentionの作業用メモリが小さくなる見込みもあるが、確かめていない。次のapplyの最初の容量の疎通で分かる。

**この決定の限界と、妥当性への脅威。**

| 懸念 | 対処 | 残る影響 |
| --- | --- | --- |
| 結果を見た後に、llama.cppの設定を変えている | 変える理由は既定から外れていたことで、速さではない。切り替えの規則も、起動の結果を見る前に決めた | なし |
| 並行数によってattentionの動き方が変わり、比べにくい | 統合に戻るのは分割で起動できなかった場合だけで、そのセルは`llama_kv`で分かる。報告ではモードを併記する | 統合に戻ったセルは、条件が違うセルとして読む |
| llama.cppの既定の`n_batch`（2,048）は大きく、混ざったステップのTPOTが膨らむ（実務なら調整する） | 既定値で要件を満たせるかを問う設計とする。チャンクの大きさをTPOTの目標から決めるのは、SLOからサービングの設定を決める別の問いである | 調整した場合の結果は範囲外 |
| pilot-1のllama.cppの並行数16（統合）と本番（分割）は条件が違う | pilot-1の値は判定に使わない。分割の値が取れたら、参考としてpilot-1と並べて記録する（判定には使わない） | 並行数16が遅かった原因のうち、統合がどれだけ効いていたかは分からない |

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 統合と分割をGPUで比べ、速い方を規則で選ぶ | 却下 | どちらを選んでも「結果を見て選んだ」と読める。既定に戻す理由は速さに依らずに立つ。比べるGPUの時間（約30分）も要らない |
| 統合のままにする | 却下 | 既定から外れた理由が無い。D7の理由（vLLMと同じ方式）は、attentionの面ではむしろ分割に当てはまる |
| 分割で起動できなければ、その並行数は「対応していない」とする | 却下 | 規則は単純だが、統合なら載ると分かっている構成を、割り当ての単位の細かさの違いだけで捨てる |
| 分割で載るように`n_ubatch`を下げる、KVを量子化する | 却下 | エンジンの調整か、モデルの振る舞いを変えることになる |
