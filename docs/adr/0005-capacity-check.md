# ADR-0005: 並行数のセルが成り立つかを、全エンジン共通の容量の判定（`capacity_check`）で確かめる

- Status: Proposed
- Date: 2026-10-19

## Context

並行数が2以上のセル（latencyパスと第3パス）では、そのエンジンのKVキャッシュに、同時に送るリクエストがすべて入りきるかを確かめる必要がある。
入りきらないと、エンジンは処理中のリクエストを中断して計算し直したり（vLLMのpreemption）、受付で待たせたりする。そうなると、測っているものが
「その並行数でのエンジンの性能」ではなく「容量不足のときの振る舞い」に変わる。

これまでの仕組み（`eval_bench/runner.py`の`parse_vllm_diagnostics`、`vllm_diagnostics`）は、1回目のapply（疎通、2026-10-18）で次の理由で働かなかった
（詳細は`docs/gpu-smoke-2026-10-18.md`のD1・D2・D7）。

- **読み取りの書式**：vLLMの起動ログから`# GPU blocks: N`と`Maximum concurrency`を読んでいたが、vLLM 0.31.0のログにはブロック数の行が無く、数字にカンマが入る。
  起動ログは人が読むための出力で、書式は版で予告なく変わる。
- **判定の基準**：`Maximum concurrency`は「すべてのリクエストが`max_model_len`（8,192）を使い切る」前提の値で、実際のリクエスト（最大約3,100トークン）よりずっと長い。
  AWQの並行数16は、実際には余裕で入るのに捨てられた。
- **vLLM専用**：llama.cppには同じ確かめが無かった。疎通では、llama.cppの並行数16は実際の出力が短かった（最大51トークン）ので回っただけで、
  最大の長さで数えると`--ctx-size 40960`には入らない。
- **エンジン間でメモリの決め方がそろっていない**：vLLMは既定でGPUの92%を使い、作業領域を先に取った残りをすべてKVにする。llama.cppは`--ctx-size`で指定した分だけKVを取る。
  疎通の「llama.cppは並行数16が載り、vLLMは載らない」は、エンジンの実力より設定の差から来ていた可能性が高い。
- **容量が起動ごとに変わる**：vLLMの起動8回のうち、新しいインスタンスで最初に起動した2回だけ、KVがちょうど1.00GiB少なかった
  （bf16は30,240トークンが22,992に、AWQは99,552トークンが92,240に。設定はすべて既定の0.92）。原因は分かっていない。

## Decision

### 1. 要件を全エンジンで同じにし、各エンジンは要件ぶんだけメモリを載せる

一般的な比べ方は2つある。(1) ハードウェアを固定し、各エンジンが設定を最善にする（MLPerf InferenceのClosed部門：モデル・精度・遅延の基準は固定し、
システムの調整は提出者に任せる）。(2) 要件（同時にc本、1リクエスト最大Lトークン、遅延の基準）を固定し、各エンジンをその要件に合わせて設定する（容量計画）。
このプロジェクトの問い（ADR-0003：この並行数で、本番のレイテンシ基準を満たせるのはどのエンジンか）は(2)の形なので、(2)を採る。

- **要件**：並行数cと、1リクエストの最大 ＝ そのセルが送るプロンプトの最大長 ＋ `max_tokens`（512で固定）。全エンジンで同じ。
- **vLLM**：`--gpu-memory-utilization`は既定の0.92のまま変えない。普段の起動で、計画した並行数（bf16は8まで、AWQは32まで）がすべて載り、
  上げても判定が変わるセルが無い（bf16の16は0.97にしても約12本で届かず、AWQの32は既定で載る。導出）。エンジンの既定値を使えば、余白の量という根拠の無い数字を持ち込まない。
- **llama.cpp**：セルごとに`--ctx-size` ＝ c × 1リクエストの最大（を切り上げた値）にし、`--kv-unified`で全スロットが共有する。`--fit off`を明示する
  （既定のonでは、設定していない引数をメモリに収まるよう黙って縮めうるため。使うコミットに`--fit`が無ければ指定しない）。
  起動したときにllama.cppが報告する実際の`n_ctx`を容量として記録する。
- **上限は探さない。** 探しても判定は変わらず、併記する数字の精度が上がるだけである。

### 2. 事前の判定：GPUの時間を使う前に、入りきるかを計算で確かめる

判定は「1リクエストの最大を割り当ての単位で切り上げ、c倍したもの ≤ KVキャッシュの容量」。この「対応」の定義は**保証型**である。
全リクエストが同時に最大の長さまで伸びても、KVが理由で受付が止まらないことを保証する。

- **プロンプトの最大長**は、手元で数える（GPUは要らない）。`run_cell`と同じ関数（`build_tool_set`・`trial_order`・`to_openai_tools_subset`）で
  そのセルが送る全リクエストを組み立て、Qwen3-8Bのトークナイザ（固定したリビジョン）の`apply_chat_template(..., add_generation_prompt=True, enable_thinking=False)`で数える。
  latencyパスはクエリの末尾の識別子（約22トークン）も含める。疎通の実測では、この数え方はvLLMの`prompt_tokens`と90件すべてで一致し（識別子の分で±1）、
  llama.cppは常に4トークン少なかった。数えた値に割り当ての単位1つ分（vLLMは16トークン）を足して、エンジン間のずれを吸収する。
  （2026-10-20訂正：「llama.cppは常に4トークン少ない」はエンジンの差ではなかった。識別子がランダムな16進数で、英字のまとまり方によってトークン数が変わり（末尾の識別子全体で16〜22）、vLLMのセルとllama.cppのセルで違う識別子を引いていたためである。llama.cppは同じテンプレートをHFと1トークンも違わず描画する（手元のb11716で確認）。識別子は数字8桁に変え、値によらずトークン数が一定になった。数え直した最大値は2,591のままで、判定は変わらない）余裕の1単位は、確かめていないエンジン間の差への備えとして残す。
- **容量**は、vLLMは`/metrics`の`vllm:cache_config_info`（`num_gpu_blocks` × `block_size`）から、サーバーの起動後に1回読む。llama.cppは起動時に報告された`n_ctx`。
- **足りないとき**：
  - vLLMは、サーバーを1回だけ起動し直して読み直す（少なく出たのは、新しいインスタンスで最初の起動だけだったため）。それでも足りなければ「対応していない」。起動し直したことも記録する。
  - llama.cppは、要件どおりの`--ctx-size`で起動できなければ（`server_not_ready`）「対応していない」。
- 「対応していない」はADR-0003のとおり結果として記録し、やり直さない。

### 3. 事後の確かめ：回した後に、容量不足が起きなかったかを確かめる

| エンジン | 確かめる値 | 出どころ |
| --- | --- | --- |
| vLLM | 中断して計算し直した回数（`vllm:num_preemptions`）のセルの前後の差が0 | `/metrics`。累積の値なので、前後の2回で取りこぼしが無い |
| llama.cpp | エラーで返ったリクエストの数と、終了理由が長さの上限だったリクエストの数が0 | 生出力。llama.cppには中断の回数にあたるメトリクスが無く、統合KVを使い切ったときの振る舞いも確かめていないため |
| 両方 | 実測したプロンプトの最大長が、事前に数えた値を超えていない | 生出力の`usage`。精度パスの生出力にも`usage`を残す |

| 事前の判定 | 事後の確かめ | 扱い |
| --- | --- | --- |
| 載らない | （回さない） | `unsupported`。結果として記録し、やり直さない |
| 載る | 問題なし | 通常の結果 |
| 載る | 問題あり | 見積もりの誤り。数字は判定に使わず、原因を調べるまで同じ構成の高い並行数は回さない。生のデータは残す |

**待ち時間は、捨てる条件に使わない。** vLLMは1ステップで処理するトークン数に上限（`max_num_batched_tokens`）があり、並行数16で約2,400トークンのプロンプトが一斉に届くと、
KVに余裕があっても後ろのリクエストは数ステップ待つ。これは並行処理のエンジンが普通に持つ挙動で、その構成の性能に含まれる。
待ちの理由別のメトリクス（`vllm:num_requests_waiting_by_reason`）も理由は`capacity`と`deferred`の2つだけで、KV不足とステップの上限を区別できない（vLLM 0.31.0のソースで確認）。
KV不足が起こす2つの現象は、受付で待たされることを事前の判定で、処理中に中断されることを事後の中断の回数で押さえる。待ち時間（`vllm:request_queue_time_seconds`の前後の差）は記録だけする。

### 4. マニフェストの`capacity_check`

vLLM専用の`vllm_diagnostics`を、全エンジン共通の`capacity_check`に置き換える。並行数が2以上のセルでは必須にする。

| 欄 | 中身 | 出どころ |
| --- | --- | --- |
| `capacity` | KVキャッシュの容量（単位・単位の大きさ・数・トークン数） | vLLMは`vllm:cache_config_info`、llama.cppは起動時の`n_ctx` |
| `required` | （1リクエストの最大 ＋ 余裕）を単位で切り上げ、c倍したもの | 事前の計算 |
| `max_prompt_tokens_planned`・`max_prompt_tokens_observed` | 事前に数えた値と、実測の最大値 | 手元のトークン化、`usage` |
| `restarts` | 容量が足りずにサーバーを起動し直した回数（vLLMのみ。0か1） | `run_cell` |
| `post_check` | vLLMは中断の回数。llama.cppはエラーの件数と打ち切りの件数 | `/metrics`の前後の差、生出力 |
| `queue_time`（vLLMのみ） | 待ち時間の合計・件数・ヒストグラムの区間ごとの件数（記録だけ） | `/metrics`の前後の差 |
| `startup_log_max_concurrency`（vLLMのみ、任意） | 起動ログの`Maximum concurrency`（照合用。読めなければ省く） | 起動ログ |

## 検討した案

| 案 | 採否 | 理由 |
| --- | --- | --- |
| 起動ログの読み取りを、0.31.0の書式に合わせて直す | 却下 | 書式は版で予告なく変わる。機械が読む値は、機械向けの口（`/metrics`）から取る |
| `Maximum concurrency`（`max_model_len`を使い切る前提）≥ c で判定する | 却下 | 実際のリクエストより2倍以上長い前提で、載る構成を捨てる |
| 待ち時間でセルを捨てる | 却下 | ステップの上限による待ちとKV不足を区別できない（3節） |
| KVキャッシュの総量そのものを全エンジンで揃える | 却下 | エンジンの効率だけを切り出すときの方法。運用で揃えるのは「1リクエストに保証する長さ」 |
| 余白をllama.cppの`--fit-target`の既定値1,024MiBにそろえる | 却下 | READMEに既定値はあるが、理由の説明が無い。issue #18390で挙がる用途は画面表示を兼ねるGPUなどデスクトップ向けで、画面の無いサーバーではOSはGPUのメモリを使わない |
| vLLMの`gpu_memory_utilization`を0.98から下げて、回せる最大の値を実測で探す | 却下 | 上げても判定が変わるセルが無い |
| llama.cppの`--ctx-size`の上限を、起動の試し直しで探す | 却下 | 判定に効かず、併記する数字の精度が上がるだけ（約10〜15分のGPUの時間） |
| 最悪の長さではなく、実際の長さ（約2,600トークン）で判定する | 却下 | 保証にならない。このワークロードではプロンプトが大半を占め、最悪の見積もりは実際の長さより約18%多いだけで、判定はほとんど変わらない（ADR-0003の追記G） |

## Consequences

- **普段の起動での容量**（導出。1リクエストの最大は、ADR-0004の追記でケースとツールの説明を直した後に`scripts/count_prompt_tokens.py`で数えた
  プロンプトの最大2,591（case_1132、カタログ2.1.1）＋ 512 ＝ 3,103トークン。vLLMは余裕16トークンを足してブロックで切り上げ、3,120）：

  | 構成 | 容量 | 保証して載る本数 | 1GiB少ない起動では |
  | --- | --- | --- | --- |
  | vLLM bf16（0.92） | 30,240トークン（実測） | 9本 | 7本 |
  | vLLM AWQ（0.92） | 99,552トークン（実測） | 31本（並行数32には288トークン足りない） | 29本 |
  | llama.cpp bf16 | `--ctx-size`しだい | 並行数16（49,648トークン）は載る見込み。空きメモリから約16〜18本（推定） | — |

  数え方は、疎通のlatencyのセル（修正前のケースとカタログ）でケースごとの最大値がvLLMの`prompt_tokens`と20件すべてで一致し、llama.cppより常に4トークン多かった。
  （2026-10-20訂正：「llama.cppは常に4トークン少ない」はエンジンの差ではなかった。識別子がランダムな16進数で、英字のまとまり方によってトークン数が変わり（末尾の識別子全体で16〜22）、vLLMのセルとllama.cppのセルで違う識別子を引いていたためである。llama.cppは同じテンプレートをHFと1トークンも違わず描画する（手元のb11716で確認）。識別子は数字8桁に変え、値によらずトークン数が一定になった。数え直した最大値は2,591のままで、判定は変わらない）
- **vLLM AWQの並行数32は「対応していない」になる。** 修正前の数え方（プロンプトの最大2,566）では余り224トークンで載っていたが、ツールの説明を直して最大が25トークン伸び、
  載らなくなった。決めたとおり、設定を上げて載せることはしない。実際の長さなら入るので、保証型を選んだことの帰結として記録する（ADR-0003の追記G）。
- **llama.cppの最大の並行数は、数字では言えない。** 上限を探さないので、「16は対応、32は対応していない」と、空きメモリからの見積もりを推定として添える。
- **llama.cppの事後の確かめは弱い。** 中断の回数にあたる値が無く、統合KVを使い切ったときの振る舞いも確かめていない。エラーと打ち切りの件数で見るが、
  黙って遅くなる形の容量不足があれば見逃す。
- **1GiB少ない起動の原因は分かっていない。** 次のapplyでも起動ごとの容量を記録し、起きるかを確かめる（手順書に書く）。
- **ADR-0003の2節「vLLMは既存の`Maximum concurrency`ガードを、latencyパスでもそのまま使う」は、このADRで置き換える。**
